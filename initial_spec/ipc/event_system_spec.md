# Техническая спецификация: Подсистема доставки событий на базе iceoryx2 (C++)

## 1. Назначение и эксплуатационные параметры
Подсистема предназначена для межпроцессной (IPC) и внутрипроцессной передачи событий от одного источника к множеству получателей (модель 1:N) с минимальной задержкой доставки и сквозным контролем целостности потока данных.

### Целевые характеристики нагрузки
* **Максимальная частота генерации:** до 1000 событий в секунду (минимальный интервал между событиями — 1 мс).
* **Профиль задержки:** минимальное время доставки (low latency) от момента генерации события до запуска обработчика на стороне приемника (единицы–десятки микросекунд).
* **Изоляция производительности:** медленные или зависшие приемники не должны блокировать или замедлять работу генератора событий.
* **Гарантия целостности:** обязательная сквозная нумерация всех событий для детектирования факта и точного количества потерь на стороне приемников и систем мониторинга.

---

## 2. Транспортная архитектура (iceoryx2)

Каждый логический канал событий идентифицируется уникальным именем сервиса и инкапсулирует два примитива `iceoryx2`:
1. **Канал данных (Publish-Subscribe):** Передача метаданных события через пользовательский заголовок (`UserHeader`) и опциональной полезной нагрузки через `Payload` без копирования памяти (zero-copy).
2. **Сигнальный канал (Event):** Связка уведомителя (`Notifier`) на стороне генератора и слушателя (`Listener`) на стороне каждого приемника для реактивного пробуждения потоков через системные механизмы ОС (`epoll` / `eventfd`).

### Политики буферизации и доставки
* **Неблокирующий генератор:** Включен режим безопасной перезаписи кольцевого буфера (`enable_safe_overflow = true`). Генератор всегда публикует событие за детерминированное время и никогда не ожидает освобождения слотов медленными приемниками.
* **Глубина буфера приемника:** Размер очереди каждого приемника по умолчанию составляет **512 сэмплов**, что обеспечивает запас автономности до 512 мс при максимальной частоте 1 кГц без потери данных при кратковременных задержках планировщика ОС.
* **Буфер истории:** Хранение последних **16 событий** в сервисе для исключения потерь на этапе асинхронного старта генератора и приемников.

## 3. Описание сущностей системы

### 3.1. Заголовок события (`EventHeader`)
Обязательная метаинформация, автоматически прикрепляемая к каждому событию при отправке:
* **Порядковый номер (`sequence_id`):** 64-битный монотонно возрастающий сквозной счетчик событий (начинается с 0). Уникален в рамках жизненного цикла генератора.
* **Временная метка (`timestamp_ns`):** 64-битное значение времени генерации события в наносекундах, снимаемое с аппаратного или монотонного системного таймера непосредственно перед публикацией.
* **Код события (`event_code`):** 32-битный идентификатор типа или категории произошедшего события.
* **Флаг полезной нагрузки (`has_payload`):** Логический признак наличия значимых дополнительных данных в теле события.

### 3.2. Маркер пустых данных (`EmptyPayload`)
Вспомогательная сущность-заглушка для каналов, передающих только заголовок (`EventHeader`) без дополнительных данных.

### 3.3. Конфигурация канала (`ChannelConfig`)
Набор параметров инициализации канала:
* Максимальное количество одновременных приемников (по умолчанию 16).
* Размер очереди каждого приемника (по умолчанию 512).
* Размер буфера истории для новых подписчиков (по умолчанию 16).
* Источник времени (`TimestampProvider`) — функция получения текущего времени в наносекундах (по умолчанию `CLOCK_MONOTONIC`).

### 3.4. Генератор событий (`EventProducer<T>`)
Шаблонная сущность-отправитель, привязанная к конкретному типу полезной нагрузки `T` (к типу `T` предъявляется строгое требование тривиальной копируемости для совместимости с разделяемой памятью).

**Основные функции:**
* Инициализация канала данных и сигнального уведомителя (`Notifier`) в разделяемой памяти.
* Выделение ячейки разделяемой памяти без копирования (zero-copy loan).
* Автоматическая фиксация временной метки и атомарный инкремент `sequence_id`.
* Публикация события (с передачей готового объекта `T`, без данных или с инициализацией поля `T` напрямую в разделяемой памяти).
* Мгновенная отправка сигнала пробуждения всем активным приемникам сразу после публикации.

### 3.5. Базовый интерфейс приемника (`IEventConsumer`)
Абстрактная нешаблонная сущность, обеспечивающая единообразное управление приемниками разных типов данных внутри единого диспетчера ожидания.

**Основные функции:**
* Полная вычитка всех накопившихся событий из очереди канала.
* Предоставление внутреннего дескриптора слушателя (`Listener`) для мультиплексирования.

### 3.6. Приемник событий (`EventConsumer<T>`)
Шаблонная сущность-получатель событий с типом полезной нагрузки `T`, реализующая интерфейс `IEventConsumer`.

**Основные функции:**
* Подписка на канал данных и регистрация собственного слушателя сигналов (`Listener`).
* Регистрация пользовательского обработчика входящих событий (`EventCallback`).
* Регистрация обработчика нарушения целостности потока (`LossCallback`).
* Неблокирующее чтение сэмплов из разделяемой памяти в цикле до полного опустошения очереди.
* Автоматическая сверка `sequence_id` каждого принятого события с ожидаемым номером, подсчет статистики потерь и сброс отслеживания при перезапуске генератора.

### 3.7. Диспетчер ожидания (`EventConsumerSet`)
Сущность-мультиплексор (обертка над `iox2::WaitSet`), позволяющая одному потоку приложения реактивно ожидать события сразу от множества разнотипных `EventConsumer<T>`.

**Основные функции:**
* Динамическое подключение (`attach`) и отключение (`detach`) приемников любых типов данных.
* Блокирующее ожидание прихода хотя бы одного события (бесконечно или с заданным таймаутом) с минимальным потреблением ресурсов CPU в простое.
* Автоматический вызов вычитки и диспетчеризации всех накопившихся событий для сработавших приемников сразу после пробуждения.
* Принудительное прерывание ожидания (`wake_up`) из другого потока для штатной остановки приложения.

## 4. Сценарии обработки нештатных ситуаций

| Событие / Аномалия | Поведение подсистемы |
| :--- | :--- |
| **Замедление или зависание одного из приемников** | Генератор продолжает публикацию без задержек. При переполнении 512 слотов буфера зависшего приемника его самые старые непрочитанные события перезаписываются новыми. Остальные приемники продолжают работу в штатном режиме. |
| **Обнаружение пропуска (`actual_seq > expected_seq`)** | Приемник вычисляет точное количество потерянных событий (`actual_seq - expected_seq`), увеличивает внутренний счетчик потерь, вызывает `LossCallback` и синхронизирует ожидаемый номер с текущим потоком. |
| **Перезапуск генератора (`actual_seq < expected_seq`)** | Приемник фиксирует сброс нумерации, уведомляет приложение через `LossCallback` и принимает новый `sequence_id` за точку отсчета. |
| **Приход нескольких событий за один такт пробуждения** | Диспетчер `EventConsumerSet` запускает полную вычитку очереди приемника до ее опустошения, гарантируя обработку всех накопленных сэмплов за один цикл пробуждения. |

---

## 5. Рекомендации по системной интеграции (Low-Latency)
Для минимизации джиттера и времени пробуждения спящего потока `EventConsumerSet` в среде Linux/POSIX рекомендуется:
* Назначить потоку, выполняющему ожидание в `EventConsumerSet`, повышенный приоритет планирования реального времени (`SCHED_FIFO`).
* Зафиксировать страницы виртуальной памяти процессов генератора и приемников в ОЗУ (`mlockall`) при инициализации для исключения задержек на обработку page faults.
* Исключить блокирующие операции ввода-вывода (запись в файлы, сетевые запросы) внутри `EventCallback`.
