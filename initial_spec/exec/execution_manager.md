# Спецификация требований к модулю Execution Manager (EM)

## 1. Введение и область применения
Настоящий документ определяет функциональные и нефункциональные требования к модулю **Execution Manager (EM)**, который выступает в качестве центрального оркестратора платформы. Модуль отвечает за управление жизненным циклом процессов, контроль состояний системы, распределение вычислительных ресурсов (включая оркестрацию ядер процессора), обеспечение безопасности выполнения программного обеспечения и отказоустойчивую очистку IPC-ресурсов на базе `iceoryx2`.

---

## 2. Управление жизненным циклом процессов (Process Lifecycle Management)

*   **REQ_EM_001: Запуск на основе зависимостей**
    *   **Описание:** EM должен запускать процессы (приложения) в строго определенном порядке, согласно дереву зависимостей, указанному в конфигурационных файлах.
    *   **Критерий приемки:** Если Приложение Б зависит от Приложения А, Приложение Б не должно начинать запуск, пока Приложение А не перейдет в рабочий статус (`kRunning`).

*   **REQ_EM_002: Контроль времени запуска (Timeout Management)**
    *   **Описание:** EM должен отслеживать время, затраченное на инициализацию каждого процесса.
    *   **Критерий приемки:** Если процесс не завершил инициализацию и не отчитался о готовности в течение заданного `startup_timeout` (в миллисекундах), EM должен принудительно завершить его (`SIGKILL`), зафиксировать ошибку в логе и применить политику восстановления.

*   **REQ_EM_003: Корректное завершение (Graceful Shutdown)**
    *   **Описание:** При остановке системы или смене состояния EM должен обеспечивать безопасное завершение работы процессов.
    *   **Критерий приемки:** EM отправляет процессу сигнал `SIGTERM` и ожидает завершения в течение `shutdown_timeout`. По истечении таймаута, если процесс еще жив, EM принудительно уничтожает его сигналом `SIGKILL`.

*   **REQ_EM_004: Автоматический перезапуск (Crash Recovery)**
    *   **Описание:** EM должен отслеживать неожиданное завершение критически важных процессов и автоматически восстанавливать их работу.
    *   **Критерий приемки:** Если процесс завершился с ненулевым кодом возврата или погиб по сигналу ОС (например, `SIGSEGV`, `SIGABRT`), EM должен предпринять попытку перезапуска согласно счетчику `restart_attempts`, указанному в манифесте.

*   **REQ_EM_014: Автоматическая очистка сегментов связи после сбоя (Crash-Safe IPC Resource Cleanup)**
    *   **Описание:** При фиксации аварийного завершения дочернего процесса (`REQ_EM_004`) модуль EM совместно с инфраструктурой `iceoryx2` должен обеспечивать автоматическое освобождение всех удерживаемых процессом коммуникационных ресурсов без вмешательства центрального брокера и без перезагрузки ЭБУ. Если процесс погиб в момент удержания заимствованного участка разделяемой памяти (`loaned sample`), система должна гарантировать обнаружение «мертвого» узла и безопасный возврат заблокированных блоков памяти обратно в общий пул издателя, предотвращая утечки памяти (Memory Leaks) и взаимные блокировки (Deadlocks) других участников обмена.
    *   **Критерий приемки:** 
        1. **Освобождение заимствованных буферов (Reclaiming Loaned Samples):** При принудительном уничтожении (`kill -9`) процесса-издателя, удерживающего сэмпл памяти (вызвавшего `loan()`, но не вызвавшего `send()`), данный блок памяти автоматически возвращается в пул доступных буферов при срабатывании механизма проверки состояния узлов (`Node::cleanup_dead_nodes()`).
        2. **Непрерывность работы для соседей (Fault Isolation):** Аварийное падение одного из процессов-подписчиков во время чтения данных из разделяемой памяти не блокирует работу процесса-издателя и других активных подписчиков. Издатель продолжает публикацию новых сообщений без ошибок исчерпания пула памяти (`OutOfMemory`).
        3. **Интеграция с циклом перезапуска EM:** Перед повторным запуском упавшего приложения согласно политике `restart_attempts`, EM вызывает процедуру очистки устаревших дескрипторов и файлов-маркеров состояния узла `iceoryx2`. Перезапущенный процесс успешно регистрирует свои сервисы и открывает каналы связи с теми же идентификаторами без ошибок конфликта имен (`AlreadyExists`) или зависших блокировок.

## 3. Управление состояниями системы (State Management)

*   **REQ_EM_005: Поддержка групп функций (Function Groups)**
    *   **Описание:** EM должен поддерживать логическое разделение системы на группы функций (например, `PrepareForSimulation`, `Simulation`, `PostPorcessing`).
    *   **Критерий приемки:** Каждая группа функций может независимо находиться в одном из состояний, определенных в конфигурации (например, `Startup`, `Running`, `SafeState`, `Shutdown`).

*   **REQ_EM_006: Синхронизация процессов с состояниями**
    *   **Описание:** EM должен автоматически запускать или останавливать процессы при изменении состояния группы функций, к которой они привязаны.
    *   **Критерий приемки:** Переход группы `ADAS` в состояние `Off` должен приводить к корректному завершению (`REQ_EM_003`) всех процессов, ассоциированных исключительно с этим состоянием.

*   **REQ_EM_007: Интерфейс управления состояниями (State Client API)**
    *   **Описание:** EM должен предоставлять межпроцессный интерфейс (API) на базе `iceoryx2` для авторизованных приложений-менеджеров состояний (State Managers) и демона PHM.
    *   **Критерий приемки:** Через API должна быть доступна функция отправки запроса на смену состояния: `SetState(group, state)`. При поступлении команды на переход в `SafeState` от демона PHM, EM обязан выполнить переключение с наивысшим приоритетом.

## 4. Управление ресурсами и безопасность (Resource & Security Management)

*   **REQ_EM_008: Ограничение вычислительных ресурсов и распределение ядер (Resource Budgets & CPU Affinity)**
    *   **Описание:** EM должен настраивать квоты процессорного времени, оперативной памяти и базовую маску доступных ядер для каждого процесса при его запуске.
    *   **Критерий приемки:** Использование механизмов ОС (Linux cgroups, `sched_setaffinity`) для жесткого ограничения лимитов `max_memory`, установки политик планировщика (`SCHED_FIFO`, `SCHED_RR`, `SCHED_OTHER`) и передачи приложению параметров разделения ядер на вычислительные (Worker cores) и сервисные/инфраструктурные (Background cores).

*   **REQ_EM_009: Запуск с минимальными привилегиями (Least Privilege)**
    *   **Описание:** EM должен запускать процессы приложений от имени непривилегированных пользователей ОС с ограниченным набором прав.
    *   **Критерий приемки:** Сброс привилегий через `setuid()`/`setgid()` после `fork()` перед вызовом `execve()`. Ни одно пользовательское приложение не должно выполняться с правами `root` (UID 0). Разрешения на установку Real-Time приоритетов для потоков выдаются точечно через Linux Capabilities (`CAP_SYS_NICE`).

*   **REQ_EM_010: Проверка целостности ПО (Authentic Execution)**
    *   **Описание:** EM должен верифицировать исполняемые файлы и их манифесты перед запуском.
    *   **Критерий приемки:** Проверка контрольной суммы (SHA-256) или криптографической подписи бинарного файла. Если проверка не пройдена, запуск блокируется, а в лог безопасности отправляется критическое событие.

## 5. Взаимодействие «Клиент-Сервер» (Execution Client API)

*   **REQ_EM_011: Подтверждение готовности приложения (State Reporting via iceoryx2)**
    *   **Описание:** EM должен предоставлять библиотечный интерфейс (SDK) для приложений, с помощью которого они сообщают свой внутренний статус инициализации.
    *   **Критерий приемки:** Приложение после внутренней инициализации и привязки своих фоновых потоков к ядрам обязано вызвать метод `ReportApplicationState(ApplicationState::Running)`. Уведомление передается в EM через легковесное событие `iceoryx2::service::messaging_pattern::Event`. До получения этого сигнала EM считает приложение находящимся в состоянии запуска.

## 6. Конфигурация (Manifest Requirements)

*   **REQ_EM_012: Декларативный манифест процессов**
    *   **Описание:** Поведение EM и параметры процессов должны настраиваться через структурированные конфигурационные файлы человекочитаемого формата (YAML/JSON).
    *   **Критерий приемки:** Манифест процесса должен содержать:
        *   `name`: Уникальное имя процесса (используется также как идентификатор узла `iceoryx2`).
        *   `executable_path` & `args`: Путь к бинарному файлу и аргументы запуска.
        *   `dependencies`: Список имен процессов, необходимых для старта.
        *   `function_groups`: Список состояний системы, в которых процесс должен быть активен.
        *   `lifecycle`: Таймауты `startup_timeout`, `shutdown_timeout` и счетчик `restart_attempts`.
        *   `resources`: Лимит RAM (`max_memory`), параметры планировщика и маски ядер (`worker_cpu_affinity`, `background_cpu_affinity`).
        *   `security`: Имя системного пользователя/группы (`uid`/`gid`).



## 7. Взаимодействие со средой выполнения и ОС (Runtime Environment)

*   **REQ_EM_013: Стандартизированный вывод логов (Logging)**
    *   **Описание:** Приложение не должно неконтролируемо писать логи в произвольные файлы на диске.
    *   **Критерий приемки:** Все лог-сообщения должны отправляться  через специализированный API логирования платформы (`nexigen::log`).

*   **REQ_EM_014: Стандартизированный вывод метрик (Metrics)**
    *   **Описание:** Приложение не должно неконтролируемо писать метрики в произвольные файлы на диске.
    *   **Критерий приемки:** Все метрики должны отправляться через специализированный API логирования платформы (`nexigen::metrics`).
