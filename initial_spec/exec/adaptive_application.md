# Спецификация требований к дочернему процессу (Adaptive Application)

## 1. Введение и область применения
Настоящий документ определяет требования к поведению, структуре, интерфейсам взаимодействия и управлению ресурсами **дочернего процесса (приложения)**, запускаемого и управляемого модулем Execution Manager (EM). Любое пользовательское или системное приложение платформы должно строго соответствовать данным правилам для обеспечения стабильности, предсказуемости и безопасности всей системы программно-определяемого автомобиля (SDV).

---

## 2. Жизненный цикл и запуск (Lifecycle & Initialization)

*   **REQ_APP_001: Запрет на самостоятельное демонизирование (No Fork/Daemonize)**
    *   **Описание:** Дочерний процесс должен запускаться на переднем плане (foreground) в рамках сессии, созданной EM.
    *   **Критерий приемки:** Приложение не должно вызывать системные функции `fork()`, `daemon()`, а также не должно отвязываться от управляющего терминала или родительского процесса.

*   **REQ_APP_002: Рапортование о готовности (State Reporting via iceoryx2)**
    *   **Описание:** Сразу после завершения внутренней инициализации (настройка памяти, привязка потоков к ядрам, открытие каналов `iceoryx2`, чтение локальных конфигураций) приложение должно уведомить EM о переходе в рабочий режим.
    *   **Критерий приемки:** Вызов функции `ReportApplicationState(Running)` в течение строго отведенного времени `startup_timeout`. Уведомление отправляется через легковесное событие `iceoryx2::service::messaging_pattern::Event`.

*   **REQ_APP_003: Обработка аргументов командной строки и переменных среды (CLI Arguments & Environment Variables)**
    *   **Описание:** Приложение должно принимать конфигурационные параметры, пути к манифестам и системные настройки (например, маски ядер, идентификатор экземпляра `instance_id`, уровни логирования), передаваемые ему EM при запуске как через аргументы командной строки, так и через переменные окружения ОС (Environment Variables).
    *   **Критерий приемки:** 
        1. Корректный парсинг стандартных векторов `int argc, char* argv[]` без аварийного завершения при передаче неизвестных флагов.
        2. Чтение переменных среды (через `std::getenv` в C++ или `std::env::var` в Rust), сформированных EM на основе манифеста процесса.
        3. Соблюдение приоритета конфигурации: аргументы командной строки переопределяют значения одноименных переменных среды, а переменные среды переопределяют значения по умолчанию, зашитые в коде или локальных файлах. При отсутствии обязательного параметра в обоих источниках процесс должен записать ошибку в лог и завершиться с ненулевым кодом возврата.

## 3. Взаимодействие со средой выполнения и ОС (Runtime Environment)

*   **REQ_APP_004: Работа в изолированном окружении (Sandbox Constraints)**
    *   **Описание:** Приложение должно успешно функционировать в рамках ограничений прав (UID/GID) и ресурсов (cgroups), наложенных EM.
    *   **Критерий приемки:** Приложение не должно запрашивать доступ к `sudo` или рассчитывать на наличие прав `root`. Память и процессорное время должны укладываться в лимиты манифеста, иначе процесс будет завершен ОС по OOM (Out Of Memory) или ограничен по CPU.

*   **REQ_APP_005: Стандартизированный вывод логов (Logging)**
    *   **Описание:** Приложение не должно неконтролируемо писать логи в произвольные файлы на диске.
    *   **Критерий приемки:** Все лог-сообщения должны отправляться либо в стандартные потоки `stdout`/`stderr` (которые перехватывает EM), либо через специализированный API логирования платформы (`nexigen::log`).

*   **REQ_APP_005_NGX_ADD: Стандартизированный вывод метрик (Metrics)**
    *   **Описание:** Приложение не должно неконтролируемо писать метрики в произвольные файлы на диске.
    *   **Критерий приемки:** Все метрики должны отправляться либо в стандартные потоки `stdout`/`stderr` (которые перехватывает EM), либо через специализированный API логирования платформы (`nexigen::metrics`).

## 4. Управление потоками и оркестрация ядер (Threading & CPU Affinity)

*   **REQ_APP_006: Разделение потоков по критичности (Thread Categorization)**
    *   **Описание:** Приложение должно четко разделять свои внутренние потоки выполнения на бизнес-логику (вычисления, обработка датчиков) и инфраструктурные/фоновые задачи.
    *   **Критерий приемки:** Выделение независимых потоков для периодического сброса логов (Logging), агрегации и отправки метрик (Metrics), обслуживания очередей связи и сохранения данных (Persistency).

*   **REQ_APP_007: Привязка инфраструктурных потоков (Background Thread Affinity)**
    *   **Описание:** Все фоновые инфраструктурные потоки (сброс логов, метрик, трассировка) должны быть жестко изолированы от основных вычислительных ядер и привязаны к выделенным «сервисным» ядрам процессора.
    *   **Критерий приемки:** Использование системных вызовов (например, `pthread_setaffinity_np` в Linux/QNX) при старте потоков логирования и метрик. Процессорная маска должна считываться из конфигурации/переменных среды приложения (например, `EASY_BG_CPU_MASK`), исключая их выполнение на ядрах, выделенных под Real-Time задачи.

*   **REQ_APP_008: Изоляция потоков бизнес-логики (Worker Thread Affinity)**
    *   **Описание:** Потоки, отвечающие за критически важные  вычисления и алгоритмы, должны иметь эксклюзивный доступ к своим ядрам процессора, чтобы минимизировать переключение контекста (Context Switch).
    *   **Критерий приемки:** Привязка основных рабочих потоков к высокопроизводительным ядрам (например, через переменную среды `EASY_WORKER_CPU_MASK`), которые физически не пересекаются с ядрами инфраструктурных потоков.

*   **REQ_APP_009: Контроль приоритетов потоков (Thread Scheduling & Priority)**
    *   **Описание:** Приложение должно явно конфигурировать политику планировщика и приоритеты для каждого типа потоков для предотвращения инверсии приоритетов.
    *   **Критерий приемки:** 
        *   Инфраструктурные потоки (логи, метрики) должны запускаться с низким приоритетом и политикой планирования `SCHED_OTHER` (или `SCHED_BATCH`).
        *   Потоки бизнес-логики реального времени должны использовать политики `SCHED_FIFO` или `SCHED_RR` с высокими приоритетами в соответствии с правами (`CAP_SYS_NICE`), выданными в манифесте EM.

## 5. Корректное завершение работы (Termination & Signals)

*   **REQ_APP_010: Обработка сигналов завершения (Signal Handling)**
    *   **Описание:** Приложение должно перехватывать системные сигналы завершения работы от EM и своевременно освобождать занятые ресурсы.
    *   **Критерий приемки:** Перехват сигнала `SIGTERM`. При получении сигнала приложение обязано остановить рабочие потоки, вернуть все заимствованные (`loaned`) буферы памяти в `iceoryx2`, корректно сбросить буферы логов на предназначенные ядра, сохранить критические данные и завершить процесс в течение отведенного времени `shutdown_timeout`.

*   **REQ_APP_011: Коды возврата (Exit Codes)**
    *   **Описание:** Приложение должно возвращать стандартизированный код завершения, информирующий EM о причинах остановки.
    *   **Критерий приемки:** 
        *   Код `0` (`EXIT_SUCCESS`) — при плановом и корректном завершении (например, по сигналу `SIGTERM`).
        *   Код отличный от `0` (например, `1` или специфический код ошибки) — при аварийном завершении по внутренней ошибке приложения.

## 6. Интеграция с Platform Health Management (PHM)

*   **REQ_APP_012: Мониторинг живого состояния (Alive Monitoring / Heartbeat)**
    *   **Описание:** Приложение должно периодически сообщать демону PHM о своей активности из каждого критически важного циклического потока.
    *   **Критерий приемки:** Вызов функции отметки `ReportCheckpoint(checkpoint_id)` внутри целевого потока через механизм событий `iceoryx2::service::messaging_pattern::Event`. Интервал вызовов должен строго соответствовать временному окну, заданному в манифесте PHM.

*   **REQ_APP_013: Логический мониторинг и контроль дедлайнов (Logical & Deadline Supervision)**
    *   **Описание:** Критические алгоритмы приложения должны сообщать PHM о порядке прохождения контрольных точек и укладываться в заданные временные рамки между ними.
    *   **Критерий приемки:** Последовательный вызов `ReportCheckpoint` для точек начала (`START`), промежуточных этапов и завершения (`END`) алгоритма. Время между `START` и `END` не должно превышать `deadline_max_duration`.

*   **REQ_APP_015: Сообщение о локальных сбоях (Health Channel Reporting)**
    *   **Описание:** Приложение должно немедленно рапортовать PHM о внутренних программно-аппаратных ошибках, которые оно не может исправить самостоятельно (например, сбой валидации сенсора, повреждение калибровок).
    *   **Критерий приемки:** Вызов функции передачи статуса ошибки в выделенный канал здоровья `ReportHealthStatus(status_id)` через `iceoryx2`.

*   **REQ_APP_016: Реакция на команды восстановления от PHM/EM (Recovery Action Handling)**
    *   **Описание:** Приложение должно быть готово к переводу текущей группы функций в аварийный режим по команде от EM/PHM.
    *   **Критерий приемки:** Приложение обязано корректно обработать внешнее уведомление о смене состояния группы функций на `SafeState`, переведя исполнительные механизмы в безопасный режим в течение заданного лимита времени.

## 7. Требования к структурам данных связи (IPC Data Constraints)

*   **REQ_APP_014: Ограничение типов данных Zero-Copy (Zero-Copy Data Type Constraints)**
    *   **Описание:** Все структуры данных, передаваемые между процессами через интерфейсы публикации/подписки (`nexigen::com`) с использованием технологии `iceoryx2`, должны иметь фиксированный размер в памяти и быть безопасными для прямого копирования байтов (память без указателей). Запрещается использование типов с динамическим выделением памяти в куче (heap allocations) и внутренних указателей (smart pointers, сырые указатели), так как адреса памяти в разных процессах не совпадают, а повреждение указателя приведет к аварийному завершению (Segmentation Fault) всех процессов-подписчиков. Для работы со строками или массивами переменной длины должны применяться специализированные типы фиксированного максимального размера.
    *   **Критерий приемки:** 
    1. Для C++ приложений: Любой тип данных T, передаваемый в методы easy::com, должен успешно проходить статическую проверку static_assert(std::is_trivially_copyable<T>::value) на этапе компиляции. Использование классов std::string, std::vector, std::unique_ptr, std::shared_ptr или виртуальных функций (содержащих указатель vptr) внутри структуры вызывает ошибку компиляции.
    2. Для Rust приложений: Передаваемый тип должен реализовывать трейт Copy (и ZeroCopySend из iceoryx2). Использование типов String, Vec<T>, Box<T>, Rc<T>, Arc<T> запрещено.
    3. Строковые данные: Для передачи текста должны использоваться контейнеры фиксированного размера, такие как iceoryx2::FixedSizeByteString<N> (или статические массивы char[N] / [u8; N]).
