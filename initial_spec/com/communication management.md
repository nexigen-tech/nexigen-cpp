# Спецификация требований к модулю Communication Management (nexigen::com) на базе iceoryx2

## 1. Введение и область применения
Настоящий документ определяет требования к функциональности, архитектуре и программным интерфейсам (API) подсистемы **Communication Management (`nexigen::com`)**. Модуль реализует сервисно-ориентированную парадигму взаимодействия (SOA), абстрагируя дочерние процессы от физической структуры бортовой сети. В качестве основного локального транспорта межпроцессного взаимодействия (IPC) используется бездемонная (daemon-less) технология **Eclipse iceoryx2**, обеспечивающая передачу данных по принципу True Zero-Copy без накладных расходов на сериализацию.

---

## 2. Модель взаимодействия (Communication Patterns)

*   **REQ_COM_001: Поддержка Событий (Publish-Subscribe на базе iceoryx2)**
    *   **Описание:** Модель связи должна поддерживать передачу данных в режиме «Издатель-Подписчик» для трансляции потоковых данных (например, кадров видеокамер, облаков точек лидара, телеметрии).
    *   **Критерий приемки:** Приложение-сервис публикует данные через абстракцию над `iceoryx2::port::publisher::Publisher`, комбинируемую с отправкой уведомления `Event` (для реактивного пробуждения подписчиков). Приложения-клиенты (`Subscriber`) получают прямой доступ к данным в разделяемой памяти.

*   **REQ_COM_002: Поддержка Методов (Methods / Request-Response)**
    *   **Описание:** Платформа должна обеспечивать выполнение удаленных процедур (RPC) в режиме «Запрос-Ответ» для выполнения разовых команд управления.
    *   **Критерий приемки:** Реализуется через двунаправленные каналы `iceoryx2` (Request-Response паттерн или спаренные очереди Pub/Sub с уникальным `correlation_id`). Вызов на стороне клиента может быть как синхронным с таймаутом, так и асинхронным (возвращающим объект `Future`).

*   **REQ_COM_003: Поддержка Полей (Fields / Get-Set-Notify)**
    *   **Описание:** Платформа должна поддерживать концепцию «Полей» — разделяемых переменных состояния сервиса, которые объединяют в себе методы чтения/записи и событие уведомления об изменении.
    *   **Критерий приемки:** Использование настройки `history_size >= 1` в `iceoryx2` для того, чтобы любой новый подписчик мгновенно получал последнее актуальное значение поля при подключении (`Get`), в сочетании с отправкой события при обновлении значения (`Notify`).

## 3. Динамический поиск сервисов (Service Discovery & Namespace)

*   **REQ_COM_004: Бездемонный поиск сервисов через iceoryx2**
    *   **Описание:** Поиск сервисов и подключение к ним должны происходить динамически в рантайме без участия центрального брокера/демона маршрутизации и без жесткой привязки к PID процессов.
    *   **Критерий приемки:** Использование встроенного в `iceoryx2` механизма децентрализованного обнаружения сервисов (`ServiceName`). Приложения могут запускаться в произвольном порядке: подписчик может ожидать появления издателя, а издатель может публиковать данные при отсутствии активных подписчиков.

## 4. Архитектурная абстракция и управление памятью (Zero-Copy & Memory Management)

*   **REQ_COM_005: Реализация True Zero-Copy передачи данных**
    *   **Описание:** Передача данных внутри одного ЭБУ/чипа между независимыми процессами должна происходить без промежуточного копирования памяти и без сериализации/десериализации.
    *   **Критерий приемки:** Использование разделяемой памяти (Shared Memory) под управлением `iceoryx2`. Приложение-издатель запрашивает кусок памяти напрямую из пула через метод `loan_uninit()`, конструирует объект на месте (in-place) и вызывает `send()`. Приложение-подписчик получает указатель `Sample<T>` на этот же физический участок памяти в режиме «только чтение» (`read-only` маппинг страниц ОС для защиты от повреждения данных подписчиком).

*   **REQ_COM_006: Протокольно-независимый API (Абстракция над транспортом)**
    *   **Описание:** Разработчик приложения должен взаимодействовать с чистым, высокоуровневым API платформы (`nexigen::com`), не привязываясь в бизнес-логике к внутренним примитивам `iceoryx2`.
    *   **Критерий приемки:** Если в будущем потребуется пробросить сервис на другой ЭБУ по сети Ethernet (через шлюз SOME/IP, DDS или Zenoh), исходный код бизнес-логики приложения не меняется. Маршрутизация настраивается исключительно на уровне манифеста и фонового сетевого моста (Gateway).

*   **REQ_COM_011: Автоматический расчет сегментов памяти (Compile-Time Memory Sizing)**
    *   **Описание:** Для снижения порога входа и исключения человеческих ошибок при написании конфигурационных файлов, модуль `nexigen::com` должен избавить разработчика от необходимости вручную высчитывать и указывать размеры структур данных в байтах (`max_sample_size`) в YAML-манифестах.
    *   **Критерий приемки:** 
        1. **Автоопределение размера и выравнивания:** При создании издателя (`Publisher<T>`) библиотека `nexigen::com` автоматически вычисляет точный размер полезной нагрузки (`sizeof(T)` в C++ / `std::mem::size_of::<T>()` в Rust) и требования к выравниванию памяти (`alignof(T)` / `std::mem::align_of::<T>()`) на этапе компиляции.
        2. **Автоматическое выделение пула (Dynamic Pool Allocation):** На основе вычисленного размера типа `T` и параметров глубины очереди (`max_samples_per_subscriber`, `max_subscribers`), библиотека автоматически запрашивает у `iceoryx2` создание сегмента разделяемой памяти нужного объема.
        3. **Защита от несовпадения версий (Type Safety Check):** При подключении подписчика `Subscriber<T>` к существующему сервису `iceoryx2`, система автоматически сверяет имя типа, его размер и выравнивание в заголовке разделяемой памяти. Если издатель и подписчик скомпилированы с разными версиями структуры `T`, подключение безопасно отклоняется с понятной ошибкой в логе (`IncompatibleTypeLayout`).

## 5. Качество обслуживания и диагностика очередей (QoS & Diagnostics)

*   **REQ_COM_007: Управление перегрузками и неблокирующая публикация (Non-Blocking Overflow Behavior)**
    *   **Описание:** Платформа должна гарантировать, что зависший или медленный процесс-подписчик не сможет исчерпать всю разделяемую память или заблокировать выполнение высокоприоритетного процесса-издателя (например, драйвера камеры).
    *   **Критерий приемки:** Конфигурирование неблокирующей политики доставки в `iceoryx2` (`UnableToDeliverStrategy::DiscardSample`). При переполнении входной очереди конкретного подписчика самый старый непрочитанный сэмпл в его очереди автоматически вытесняется новым, а издатель продолжает работу со временем выполнения `O(1)` без ожидания.

*   **REQ_COM_008: Изоляция инфраструктурных потоков связи**
    *   **Описание:** Любые вспомогательные фоновые задачи модуля связи (например, работа сетевых мостов Gateway для проброса трафика из `iceoryx2` во внешний Ethernet, сбор статистики обмена, фоновые циклы `WaitSet` для некритичных сервисов) должны быть изолированы от ядер реального времени.
    *   **Критерий приемки:** Инфраструктурные потоки модуля `nexigen::com` при инициализации автоматически считывают переменную окружения/манифест (`EASY_BG_CPU_MASK`) и жестко привязываются к сервисным ядрам процессора с помощью `pthread_setaffinity_np`.

*   **REQ_COM_012: Проактивная детекция отставания подписчика (Subscriber Lag & Queue Overflow Detection)**
    *   **Описание:** Модуль `nexigen::com` должен отслеживать здоровье коммуникационных очередей и предоставлять приложениям и демону PHM механизм раннего обнаружения деградации производительности подписчиков (когда подписчик читает данные медленнее, чем издатель их публикует).
    *   **Критерий приемки:** 
        1. **Мониторинг заполнения буфера:** При вызове метода публикации `send()` (или при чтении на стороне подписчика) прослойка `nexigen::com` проверяет текущий уровень заполнения очереди подписчика и факт потери пакетов (перезаписи кольцевого буфера).
        2. **Генерация предупреждений (Backpressure Telemetry):** Если очередь критического подписчика заполнена более чем на заданный порог (по умолчанию 80%) или зафиксирован факт вытеснения непрочитанного сэмпла (`SampleLost`), библиотека `nexigen::com` автоматически инкрементирует счетчик телеметрии и (опционально по настройке манифеста) отправляет уведомление о деградации в канал здоровья PHM (`REQ_PHM_004`).

## 6. Конфигурация (Service Manifest)

*   **REQ_COM_009: Минималистичный манифест конфигурации сервисов**
    *   **Описание:** Благодаря автоматическому расчету размеров типов (`REQ_COM_011`), конфигурация сервисов в YAML-манифесте приложения должна быть максимально простой и содержать только архитектурные параметры и политики качества обслуживания (QoS).
    *   **Критерий приемки:** Секция `communication` в манифесте процесса должна содержать только высокоуровневые настройки:
        *   `provided_services`: Список публикуемых сервисов (имя сервиса `service_name`, максимальное число подписчиков `max_subscribers`, глубина истории `history_size`).
        *   `required_services`: Список потребляемых сервисов (имя сервиса `service_name`, размер приемного буфера `buffer_capacity`, флаг критичности потери пакетов `report_overflow_to_phm`).
