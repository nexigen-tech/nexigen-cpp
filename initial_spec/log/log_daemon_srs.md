# Спецификация требований к демону логирования (LogDaemon)

## 1. Введение и область применения
Настоящий документ определяет требования к центральному системному демону **`LogDaemon`**. Демон выступает единой точкой сбора, маршрутизации, дискового хранения и сетевой трансляции всех логов платформы. `LogDaemon` получает сырые бинарные фреймы из разделяемой памяти **iceoryx2**, производит многоуровневую фильтрацию по приемникам (диск, сеть, аварийный буфер), форматирует данные и обеспечивает их надежное хранение без влияния на вычислительные ядра реального времени.

---

## 2. Жизненный цикл и системное окружение (Lifecycle & Infrastructure)

*   **REQ_LOGD_001: Ранний запуск под управлением EM**
    *   **Описание:** `LogDaemon` запускается модулем Execution Manager (EM) на самом первом этапе инициализации системы.
    *   **Критерий приемки:** В системном манифесте EM демон имеет приоритет старта №1 в состоянии `MachineState::Startup` (до запуска PHM, State Manager и приложений). Демон рапортует о готовности вызовом `ReportApplicationState(Running)`.

*   **REQ_LOGD_002: Изоляция на сервисных ядрах и приоритеты (CPU Affinity & Resource Limits)**
    *   **Описание:** Все потоки демона (прием сообщений, форматирование, запись на диск, сетевая отправка) должны выполняться исключительно на выделенных сервисных ядрах процессора.
    *   **Критерий приемки:** 
        1. Жесткая привязка потоков демона к сервисному ядру (считывается из `EASY_BG_CPU_MASK`) через `pthread_setaffinity_np`.
        2. Политика планирования процессов `SCHED_OTHER` или `SCHED_BATCH` с низким приоритетом (`nice = 10..15`), исключающая вытеснение потоков бизнес-логики.
        3. Квотирование дискового ввода-вывода через `cgroups` (`io.max` / `blkio.throttle`).

*   **REQ_LOGD_003: Реактивный сбор без поллинга (Event-Driven WaitSet Processing)**
    *   **Описание:** Демон должен переходить в режим сна при отсутствии сообщений и просыпаться только по аппаратным/системным прерываниям от `iceoryx2`.
    *   **Критерий приемки:** Использование `iceoryx2::waitset::WaitSet`. Пробуждение потока происходит по событию отправки нового лога от любого процесса либо по системному таймеру пакетного сброса (например, каждые 50 мс). В режиме отсутствия логов загрузка CPU демоном составляет 0%.

## 3. Маршрутизация и раздельная фильтрация по приемникам (Sink-Specific Filtering)

*   **REQ_LOGD_004: Независимая маршрутизация потоков (Multi-Sink Architecture)**
    *   **Описание:** Демон должен поддерживать параллельную отправку одного и того же входящего лог-сообщения в три независимых приемника: **Persistent Storage Sink** (накопитель), **Network Streaming Sink** (сеть) и **Crash Ring-Buffer Sink** (буфер аварийного дампа в RAM).

*   **REQ_LOGD_005: Фильтрация для накопителя (Storage Sink Filter)**
    *   **Описание:** Для защиты ресурса перезаписи флеш-памяти (eMMC/UFS) на диск должны сбрасываться только критические и ключевые эксплуатационные события.
    *   **Критерий приемки:** По умолчанию на диск пропускаются только события уровня `>= Warn` (`Warn`, `Error`, `Fatal`), а также события `Info` от доверенных системных контекстов (EM, SM, PHM). Отладочные сообщения (`Debug`, `Verbose`) на диск блокируются.

*   **REQ_LOGD_006: Фильтрация для сетевого стриминга (Network Sink Filter)**
    *   **Описание:** Сетевой канал должен позволять транслировать детальный отладочный трафик без засорения диска.
    *   **Критерий приемки:** Сетевой фильтр настраивается независимо от дискового. При подключении внешнего клиента демон может транслировать поток `Debug`/`Verbose` для выбранного `app_id` по сети, не изменяя жесткие фильтры записи на диск.

*   **REQ_LOGD_007: Защита от перегрузки и подавление спама (Rate Limiting & Throttling)**
    *   **Описание:** Аварийное зацикливание приложения с непрерывной генерацией сообщений об ошибках не должно переполнять накопитель и сеть.
    *   **Критерий приемки:** Если для пары `(app_id, context_id)` частота однотипных сообщений превышает лимит (например, более 50 сообщений в секунду), демон пропускает первое сообщение, временно глушит последующие и по окончании секундного окна выводит сводную строку вида: `[THROTTLED] Context SENS: 450 identical messages suppressed`.

## 4. Сохранение на диск и кольцевая ротация (Storage Management)

*   **REQ_LOGD_008: Пакетная асинхронная запись (Buffered Batch I/O)**
    *   **Описание:** Запись логов на диск должна осуществляться крупными блоками для снижения количества операций ввода-вывода.
    *   **Критерий приемки:** 
        1. Логи агрегируются в промежуточном буфере демона и сбрасываются на диск блоками по 64 КБ (или по истечении таймаута не более 500 мс).
        2. Форматирование бинарного `LogFrame` в текстовую строку (с добавлением даты, PID и имени контекста) происходит непосредственно перед записью в буфер на сервисном ядре.

*   **REQ_LOGD_009: Контроль дисковой квоты и ротация файлов (Log Rotation)**
    *   **Описание:** Подсистема логирования не должна приводить к переполнению файловой системы накопителя.
    *   **Критерий приемки:** 
        1. Максимальный размер активного файла лога ограничен параметром `max_file_size_mb` (например, 20 МБ).
        2. Максимальное число архивных файлов ограничено параметром `max_archive_files` (например, 5 файлов).
        3. При достижении предела размера текущий файл закрывается, переименовывается с добавлением метки времени, а самый старый архив удаляется.
        4. Закрытые архивы сжимаются в фоновом потоке алгоритмом `zstd` с минимальным приоритетом ввода-вывода.

*   **REQ_LOGD_010: Гарантированный сброс при аварии (Crash & Shutdown Flush)**
    *   **Описание:** При экстренном останове или критическом сбое системы накопленные логи должны быть гарантированно зафиксированы на накопителе.
    *   **Критерий приемки:** 
        1. При получении сигнала `SIGTERM` от EM или события перехода в `SafeState` демон вычитывает остаток очереди `iceoryx2` и выполняет блокирующий системный вызов `fsync()` для текущего файла лога.
        2. Кольцевой буфер аварийного дампа в RAM (хранящий последние 2 000 сообщений любого уровня, включая `Debug`) при наступлении аварии целиком сбрасывается в отдельный файл `crash_dump_<timestamp>.log`.

## 5. Сетевая трансляция и динамическое управление (Network Sinks & Control)

*   **REQ_LOGD_011: Трансляция по протоколам UDP и TCP**
    *   **Описание:** Демон должен обеспечивать передачу логов внешним потребителям (компьютер разработчика, отладочный стенд) через сеть Ethernet.
    *   **Критерий приемки:** 
        1. **UDP Multicast / Unicast:** Неблокирующая трансляция логов в режиме реального времени на заданный IP и порт. Потеря сетевых пакетов не влияет на запись файлов на диск.
        2. **TCP Server:** Предоставление управляющего порта для подключения CLI-утилиты отладки с авторизацией и гарантированной доставкой.

*   **REQ_LOGD_012: Управление уровнями на лету (Runtime Level Control API)**
    *   **Описание:** Демон должен обрабатывать внешние запросы на временное изменение активных уровней логирования в запущенных процессах.
    *   **Критерий приемки:** По команде из сети (или от UDS диагностики) демон обновляет значение порога в разделяемой памяти `iceoryx2` для целевого `app_id`. Клиентские библиотеки подхватывают изменение мгновенно согласно `REQ_LOGC_003`.

## 6. Конфигурация (LogDaemon Manifest)

*   **REQ_LOGD_013: Декларативная конфигурация демона**
    *   **Описание:** Все параметры работы демона описываются в едином файле конфигурации `log_daemon_config.yaml`.
    *   **Критерий приемки:** Манифест содержит:
        *   `storage`: путь к каталогу хранения `log_directory`, порог важности для записи `min_log_level_storage`, лимиты `max_file_size_mb`, `max_archive_files`, интервал сброса `flush_interval_ms`.
        *   `network`: флаг активности `enable_streaming`, протокол `protocol` (`udp`/`tcp`), целевой адрес `ip`, порт `port`, порог важности `min_log_level_network`.
        *   `throttling`: лимит сообщений `max_messages_per_sec_per_context`.
        *   `resources`: маска сервисных ядер `bg_cpu_affinity`.
