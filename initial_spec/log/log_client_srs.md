# Спецификация требований к клиентской библиотеке логирования (easy::log SDK)

## 1. Введение и область применения
Настоящий документ определяет требования к функциональности, производительности и программному интерфейсу (API) встраиваемой библиотеки **`nexigen::log`**. Библиотека линкуется с дочерними процессами платформы и обеспечивает ультрабыстрое формирование лог-событий с передачей через разделяемую память **iceoryx2** без динамических аллокаций памяти и без блокировок потоков реального времени.

---

## 2. Уровни логирования и ранняя фильтрация (Early Filtering)

*   **REQ_LOGC_001: Иерархия уровней логирования (Log Levels)**
    *   **Описание:** Библиотека должна поддерживать строгую шкалу приоритетов сообщений: `Off` (0), `Fatal` (1), `Error` (2), `Warn` (3), `Info` (4), `Debug` (5), `Verbose` (6).
    *   **Критерий приемки:** Определение перечисления `LogLevel` в публичном API библиотеки.

*   **REQ_LOGC_002: Мгновенное раннее отсечение (Zero-Cost Early Filtering)**
    *   **Описание:** Если уровень важности вызываемого сообщения ниже текущего активного порога контекста, вызов функции логирования должен прерываться немедленно, не выполняя вычисление аргументов, форматирование строк и обращение к IPC.
    *   **Критерий приемки:** 
        1. Проверка условия `message_level <= context.active_level` выполняется первой инструкцией вызова через атомарное чтение (`std::memory_order_relaxed`).
        2. Время выполнения отсеченного вызова не должно превышать **2 наносекунд** (1–2 процессорные инструкции `cmp` + условный переход).
        3. Макросы логирования гарантируют, что выражения аргументов (например, `log.Debug("Data: {}", compute_heavy_crc())`) не вычисляются при отключенном уровне.

*   **REQ_LOGC_003: Динамическое обновление порогов (Dynamic Level Sync)**
    *   **Описание:** Порог активного уровня логирования для каждого контекста должен поддерживать обновление на лету без перезапуска процесса.
    *   **Критерий приемки:** Порог считывается при старте из локального манифеста, а в рантайме синхронизируется через разделяемую память `iceoryx2` (паттерн «Поле» / Shared Atomic State), управляемую со стороны `LogDaemon`.

## 3. Модель данных и Zero-Copy транспорт (iceoryx2 Data Path)

*   **REQ_LOGC_004: Фиксированная структура фрейма (TriviallyCopyable LogFrame)**
    *   **Описание:** Сообщения должны упаковываться в строго типизированную бинарную структуру фиксированного размера без указателей и динамических буферов (`REQ_APP_014`).
    *   **Критерий приемки:** 
        1. Структура `LogFrame` имеет фиксированный размер (256 байт) и удовлетворяет условию `std::is_trivially_copyable<LogFrame>::value`.
        2. Структура содержит: `timestamp_ns` (монотонное время ОС), `app_id` (4 байта), `context_id` (4 байта), `thread_id` (4 байта), `log_level` (1 байт), `payload_size` (2 байта), `dropped_counter` (4 байта) и статический буфер данных `payload[232]`.

*   **REQ_LOGC_005: Заимствование памяти Zero-Copy (Loaned In-Place Construction)**
    *   **Описание:** При успешном прохождении порога важности запись данных должна производиться непосредственно в разделяемую память `iceoryx2` без промежуточных локальных буферов.
    *   **Критерий приемки:** 
        1. Вызов метода `publisher.loan_uninit()` для получения ячейки памяти напрямую из сегмента `iceoryx2`.
        2. Конструирование `LogFrame` по месту (in-place) и немедленная публикация через `send()`.
        3. Уведомление демона отправляется через примитив `iceoryx2::service::messaging_pattern::Event`.

## 4. Гарантии реального времени и обработка переполнений (Real-Time Guarantees)

*   **REQ_LOGC_006: Отсутствие блокировок и аллокаций (Lock-Free / Allocation-Free)**
    *   **Описание:** Вызов логирования в потоках бизнес-логики и потоках жесткого реального времени (`SCHED_FIFO`) не должен вызывать блокировки мьютексов, вызовы распределителя памяти (`malloc`/`new`) или системные вызовы ввода-вывода (syscalls).
    *   **Критерий приемки:** Полное отсутствие динамических аллокаций в критическом пути логирования. Время худшего случая (WCET) для успешной отправки фрейма в `iceoryx2` не превышает **1.5 микросекунды**.

*   **REQ_LOGC_007: Неблокирующее вытеснение и счетчик потерь (Non-Blocking Drop Counter)**
    *   **Описание:** Если очередь логов в разделяемой памяти переполнена (например, из-за медленного чтения демоном), клиентский вызов не должен ждать освобождения слота.
    *   **Критерий приемки:** 
        1. Использование неблокирующей политики: при отказе в аллокации слота или переполнении буфера слот не ожидается, а инкрементируется локальный атомарный счетчик `local_dropped_count`.
        2. Значение `local_dropped_count` помещается в следующий успешно отправленный `LogFrame`, после чего счетчик сбрасывается в 0.

*   **REQ_LOGC_008: Выделенный аварийный канал (Emergency Reserved Queue)**
    *   **Описание:** Сообщения уровней `Fatal` и `Error` не должны теряться из-за спама информационными сообщениями в штатной очереди.
    *   **Критерий приемки:** Для сообщений `Fatal` и `Error` библиотека использует выделенный резервный канал публикации `iceoryx2` с гарантированным пулом свободных буферов.
