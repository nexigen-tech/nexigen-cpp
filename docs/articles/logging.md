# Логирование в nexigen: бюджет, запись и контракт

У потока управления дроном бюджет на такт — микросекунды, и половину его может съесть один `printf`. Поэтому логирование в реальном времени проектируют не как вывод текста, а как бюджет: сколько наносекунд стоит запись, что происходит при переполнении и кто платит за форматирование. В `nexigen::logging` этот бюджет назван явно — 20 наносекунд на принятую запись, — и почти каждое решение в подсистеме объясняется попыткой в него уложиться: отдельные SPSC-кольца на поток, отложенное форматирование, кэшированный `gettid`, калиброванный TSC вместо `clock_gettime`. Эта статья — разбор того, как из одного числа вырастает архитектура.

У системы два шва, и о них стоит договориться сразу. Первый — между продюсером и потребителем: вызывающий поток только пакует запись, а рендерит и пишет её один фоновый поток. Второй — между процессом и демоном: `Iceoryx2Logger` публикует фиксированный кадр в shared memory, а `nexigen-logd` превращает поток кадров в один файл. Почти всё остальное — следствия этих двух границ.

## Что значит «записать лог»

Публичная поверхность намеренно маленькая. У логгера есть шесть удобных методов (`verbose`, `debug`, `info`, `warning`, `error`, `fatal`), один явный `log(level, ...)`, управление порогом `set_level`/`level()` и барьер `flush()`:

```cpp
nexigen::logging::FileLogger<> logger;

logger.info("calibration lost: sensor={} frame={}", sensor_id, frame);
logger.warning("retrying after {} ms", backoff_ms);
logger.set_level(nexigen::core::LogLevel::Warning);
```

Формат — не произвольная строка. Первый параметр имеет тип `FormatWithLocation<Args...>`, который собирает `std::format_string<Args...>` и `std::source_location` в одном `consteval`-конструкторе. Отсюда два следствия. Во-первых, несоответствие формата и аргументов — ошибка компиляции, а не runtime-сюрприз. Во-вторых, `source_location::current()` вычисляется в точке вызова, поэтому запись несёт файл, строку и функцию вызывающего кода, а не внутренности библиотеки. Нелитеральный формат-string тоже не компилируется: `consteval`-конструктор требует константу.

Отдельная деталь — `format_param_t<Args...>`. Если написать параметр как `FormatWithLocation<Args...>`, то `Args` начнут выводиться из литерала `const char[N]`, литерал не сматчится с шаблоном класса, и вывод типов сломается до того, как сработает `consteval`-преобразование. Поэтому логгер принимает `detail::format_param_t<Args...>` — identity-алиас, который делает параметр non-deduced: `Args` выводятся только из хвостовых аргументов, а литерал потом конвертируется одним пользовательским преобразованием.

Контракт зафиксирован концептом. В `nexigen::core` он не знает про логирование и принимает шаблон формата параметром:

```cpp
template <class T, template <class...> class Format>
concept Logger = requires(T t, const T ct, LogLevel level) {
    { t.set_level(level) } noexcept -> std::same_as<void>;
    { ct.level() } noexcept -> std::same_as<LogLevel>;
    { t.log(level, std::declval<Format<>>()) } noexcept -> std::same_as<void>;
    // ... шесть convenience-методов ...
    { t.flush() } noexcept -> std::same_as<Status>;
};
```

Рядом в `core::concepts` живут ещё две формы, которые важны для стыковки. `LevelLogger` — минимальный контракт «уровень + готовая строка» для воркеров и сервисов, которым не нужны ни формат, ни кольца, ни `flush()`; его принимают там, где достаточно диагностического канала. `Message` — это ровно `std::is_trivially_copyable_v<T>`; ему удовлетворяют и `LogRecord`, и `LogFrame`, и именно это свойство позволяет передавать кадр через shared memory без сериализации. Полный `Logger` — надмножество: формат, шесть удобств и барьер.

`nexigen::logging::concepts::Logger<T>` — это алиас `core::concepts::Logger<T, FormatWithLocation>`. Важная часть контракта: методы записи возвращают `void` и помечены `noexcept`. Ошибку нельзя вернуть вызывающему, и это не недосмотр: на горячем пути нет места ни исключению, ни `Status`, который никто не проверит. Единственный метод, возвращающий `core::Status`, — `flush()`, и он относится к control plane.

Каждый конкретный логгер пинит соответствие концепту `static_assert`-ом в своём заголовке. Это ловит расхождение сигнатур на этапе сборки библиотеки, а не в первом приложении, которое попробует новый сток.

## Семь шагов горячего пути

Вся принятая запись проходит один и тот же конвейер из `detail::Producer`. Порядок шагов зафиксирован, потому что именно против него тратится бюджет: 20 наносекунд на принятую запись. Это бюджет только продюсера — рендеринг, запись в файл и публикация кадра в него не входят.

| Шаг | Устойчивая работа | Цена |
|---|---|---|
| 1. Фильтр уровня | relaxed load + compare | ~1 нс по оценке в коде; гейт теста: медиана ≤ 3 нс, p99.9 ≤ 2 нс |
| 2. Слот шарда | чтение TLS-кэша | 0 общих атомиков в установившемся режиме; первый вызов — один `fetch_add` |
| 3. Идентификатор потока | чтение TLS | syscall только на первом вызове потока |
| 4. Метка времени | sample TSC + clamp | без атомиков; калибровка ~2 мс на слот при `initialize()` |
| 5. Оконный throttle | compare по полям шарда | 0, если выключен; редкое деление на границе окна |
| 6. Упаковка аргументов | `memcpy` на аргумент | без аллокаций и форматирования |
| 7. `try_push` | release-store | wait-free; полное кольцо — дроп и `buffer_full` |

Числа в таблице разной природы. «20 нс» — заявленный бюджет и гейт `tests/logging/latency_test.cpp`; «~1 нс» — оценка из комментария к фильтру; «~2 мс» — стоимость холодной калибровки; остальные строки описывают количество операций, а не измеренное время. Тест меряет именно enqueue: `Producer<8192, 128, 1>`, best-of-3 в строгой Release-конфигурации, продюсер и потребитель на разных ядрах, накладные расходы измерения вычитаются, аллокации проверяются отдельно. Потребитель в тесте спит, а не крутится: иначе перезагрузка tail-линии продюсера оплачивалась бы в медиану enqueue.

### 1. Фильтр уровня

Самая дешёвая и самая важная проверка. Порог лежит в `detail::LevelControl` — одном relaxed-атомике на отдельной кэш-линии. Вызов читает его, сравнивает с уровнем записи и, если запись ниже, заканчивается здесь. Ни метки времени, ни TLS-кэша слота, ни кольца не происходит.

В коде это оценено примерно в 1 нс. Тест ставит более строгие границы для короткозамкнутого пути: медиана ≤ 3 нс, p99.9 ≤ 2 нс (спецификация называет потолок 2 нс / 10 тактов). Для системы, где `debug` включён только на стенде, это означает, что выключенный уровень в проде стоит почти ноль.

### 2. Слот шарда

Пул ищет слот текущего потока в `thread_local`-кэше. Первый вызов потока для конкретного пула клеймит слот одним relaxed `fetch_add` на общем счётчике и публикует высокую отметку; дальше поток читает только свой TLS. В установившемся режиме на принятом пути нет общих атомиков — ни CAS, ни `fetch_add`, ни спина.

Если слотов больше нет, `claim_slot()` возвращает `-1`, запись отбрасывается и учитывается как `slot_exhausted`. Это не ошибка конфигурации, а штатный отказ: блокировать продюсера нельзя. Цена шага в установившемся режиме — чтение TLS; цена первого вызова — один RMW и одна release-публикация.

### 3. Идентификатор потока

`gettid` кэшируется в `thread_local`: syscall `SYS_gettid` выполняется один раз на поток, дальше читается положительное число. Ноль служит признаком «ещё не разрешено», поэтому отдельный флаг не нужен. В установившемся режиме шаг стоит одно чтение TLS.

### 4. Метка времени

Вместо `clock_gettime` на каждый вызов используется `StampSource`, калиброванный при `initialize()`. Источник — один на слот, то есть single-writer: повторная калибровка и монотонный clamp не требуют атомиков и не гоняются с другими потоками. Домен — канонические монотонные наносекунды проекта; перевод в UTC — задача потребителя и часового домена, а не продюсера.

Калибровка стоит примерно 2 мс на слот и делается на холодном пути. Для 32 слотов это заметная, но разовая плата при старте. На горячем пути остаётся sample TSC и clamp; это дешевле syscall и не создаёт общей точки конкуренции.

### 5. Оконный throttle

Необязательный шаг. Если `ThrottleConfig` выключен, он не стоит ничего. Если включён, это обычное состояние шарда: `window_start_ns` и `tokens_used`, один unsigned-compare на установившемся вызове. На границе окна допускается одно деление, чтобы догнать пропущенные окна, и, возможно, синтез сводки о дропах. Исчерпание бюджета — дроп с причиной `rate_limited`.

Важно, что это не token bucket анти-спама: оконный throttle включается конфигурацией файлового или iceoryx2-логгера, а двухступенчатый `SpamProtection` живёт отдельно и по умолчанию выключен.

### 6. Упаковка аргументов

Единственная работа с данными на горячем пути: `memcpy` каждого аргумента в фиксированный inline-блоб по compile-time смещениям. Никакого `std::format`, никакой локали, никакого преобразования чисел в строки. Смещения — чистая функция от `(MessageCapacity, Args...)`, поэтому упаковщик и рендерер выводят одну таблицу из одного pack. Если pack не влезает, срабатывает `static_assert` — до runtime-кода.

Цена — один `memcpy` на аргумент плюс запись нескольких полей заголовка. Для `std::string_view` дополнительно копируется inline-содержимое и ставится флаг усечения. Аллокаций нет ни на одном пути.

### 7. `try_push`

Последний шаг — `try_push` в кольцо своего шарда. Это wait-free release-store; если кольцо полно, запись отбрасывается и инкрементируется `buffer_full`. Продюсер никогда не ждёт потребителя и не проверяет, успел ли тот что-то слить.

Между упаковкой и `try_push` стоят ещё две проверки анти-спама. Они выключены по умолчанию; при включённом подавлении повторов хэш стоит около 70 нс и в бюджет 20 нс уже не влезает — это осознанный размен, о котором ниже.

### Что осталось за бюджетом

В 20 нс не входят: рендеринг отложенного формата, JSON-экранирование, `fsync`, ротация и публикация кадра в shared memory. Всё это делает потребитель. В комментарии к `Iceoryx2Sink` стоимость публикации оценена примерно в 278 нс на кадр — она ложится на рабочий поток, а не на продюсера. Поэтому «20 нс» — это цена записи в кольцо, а не цена появления строки на диске.

## Запись, которая ничего не форматирует

`LogRecord` — это value type, который пересекает границу продюсер/потребитель. Он выглядит как структура с указателями, но все указатели ссылаются либо на статическое хранилище программы, либо на собственный блоб записи. Формат-литерал живёт в образе, строки `source_location` — в статической таблице компилятора, аргументы скопированы в `arg_payload_` при emit. Ничего не аллоцируется, ничего не висит на памяти вызывающего.

Раскладка при `MessageCapacity = 200` (ровно 256 байт, четыре кэш-линии):

```text
  0   stamp          chrono::Timestamp, монотонные нс
  8   thread_id      uint32, кэшированный SYS_gettid
 12   level          core::LogLevel, один байт
 13   flags          bit0 — аргументы усечены, bit1 — усечён рендер
 14   arg_length     uint16, сколько байт блоба занято
 16   file_name      const char*, статическое хранилище
 24   function_name  const char*, статическое хранилище
 32   line           uint32, строка вызова
 40   fmt            const char*, литерал формата
 48   render         указатель на type-erased рендерер
 56   arg_payload_   inline-блоб аргументов
```

При дефолтном `MessageCapacity = 128` запись меньше 256 байт, но по-прежнему выровнена на кэш-линию (`alignas(64)`). Ёмкость блоба задаётся `NEXIGEN_LOG_MESSAGE_CAPACITY` и должна лежать в `[16, 0xFFFF]`: длина хранится в `uint16`.

Упаковка аргументов устроена просто и жёстко. Каждый нестроковый аргумент занимает ровно 8 байт: значение должно быть trivially copyable, поэтому `memcpy` туда и обратно не создаёт ни alignment-, ни lifetime-проблем. `std::string_view` занимает слот `2 + MessageCapacity / 2` байт: двухбайтовая длина и inline-копия. Смещения — чистая функция от `(MessageCapacity, Args...)`, поэтому упаковщик и рендерер выводят одну и ту же таблицу из одного и того же pack. Если pack не влезает в блоб, срабатывает `static_assert` — до любого runtime-кода. Усечение возможно только у строкового содержимого, и оно поднимает бит `flag_args_truncated`.

Набор допустимых типов задан концептом `Packable`: арифметика, enum, `chrono::Timestamp`, `std::string_view`, `const char*`, `void*`, `const void*`. Всё остальное — ошибка компиляции, а не runtime-отказ. Это осознанное ограничение: произвольный пользовательский тип потребовал бы либо аллокации, либо собственного формата сериализации на горячем пути.

Рендеринг делает потребитель. `render_into(out, cap)` вызывает type-erased callback, сгенерированный для конкретного pack, и тот выполняет `std::vformat_to` в предоставленный scratch. Потребитель владеет scratch-буфером, поэтому аллокаций нет и на его стороне. Если текст не влез, выставляется `flag_render_truncated`, а возвращённая длина всегда авторитетна: сток копирует ровно её, поэтому наполовину записанной строки не бывает.

Именно этот шов — «записать» отдельно от «отформатировать» — делает остальную архитектуру возможной. Продюсер не знает, куда пойдёт запись: в консоль, в JSON-файл или в shared memory. Он знает только, что должен упаковать аргументы и отдать запись в кольцо.

## Шарды: почему у каждого потока своё кольцо

Одно кольцо на нескольких продюсеров потребовало бы CAS-цикла на каждом push. Поэтому пул устроен как массив SPSC-колец: каждый поток-продюсер владеет ровно одним кольцом, а единственный потребитель — фоновый поток логгера — обходит их по кругу.

```text
  thread A ---> [ shard 0: SPSC ring ] --+
  thread B ---> [ shard 1: SPSC ring ] --+--> AsyncWorker (единственный потребитель)
  thread C ---> [ shard 2: SPSC ring ] --+
       ...                ...
  thread N ---> [ shard N: SPSC ring ] --+
```

У SPSC-кольца один продюсер и один потребитель, индексы монотонны, а каждый индекс живёт на своей кэш-линии. Общая ёмкость пула — `ShardCapacity × MaxThreads`; у `FileLogger<>` по умолчанию это 128 × 32 = 4096 записей, у `ConsoleLogger<>` — столько же, у `Iceoryx2Logger<>` — тоже. Потоки сверх `MaxThreads` не блокируются: их записи уходят в `slot_exhausted`.

Пул хранит высокую отметку зарегистрированных слотов; потребитель ограничивает обход ею, поэтому не сканирует пустые шарды. Клейм слота кэшируется в `thread_local` и перепроверяется по высокой отметке — это защита от случая, когда пул уничтожили и создали заново по тому же адресу.

Из этой схемы следует, что логгеры non-copyable и non-movable: кольца должны сохранять адреса, а TLS-кэш слота привязан к адресу пула. В примерах логгеры поэтому лежат в статическом хранилище, а не в `std::vector`.

## Один потребитель: рабочий поток

`detail::AsyncWorker` — это один `std::jthread` на логгер. Его обязанности целиком лежат вне горячего пути: батч-дрейн всех шардов, рендеринг отложенных форматов в scratch стока, передача строки в сток, ответ на `flush()` и финальный дрейн при остановке.

Дрейн устроен как ограниченный батч: до 64 записей за проход, при этом `pop()` обходит шарды round-robin и снимает не больше 16 записей с одного шарда за проход. Это защита от голодания: один поток, заливший свой шард, не должен навсегда занять потребителя.

Из round-robin следует важная деталь: порядок строк в файле — это порядок дрейн-а, а не глобальная сортировка по метке времени. Запись из второго шарда может оказаться ниже записи из первого, хотя её `timestamp` раньше. Для корреляции нужно смотреть на поля времени, а не на номер строки.

Когда кольца пусты, потребитель не крутится в busy-poll. Он делает несколько неудачных проходов (spin budget), затем засыпает, и сон растёт геометрически от 100 мкс до `worker_poll_interval_us` (по умолчанию 1 мс). Сразу после активности реакция укладывается в ~100 мкс, а долгий простой стоит одного пробуждения на интервал. Дополнительно рабочий поток расширяет timer slack до половины интервала, чтобы несколько логгеров, пришпиленных к одному ядру, просыпались одним слитым всплеском, а не N отдельными.

У `flush()` свой handshake на трёх атомиках в одной padded-ячейке. Вызывающий делает `fetch_add(release)` в `requested` — это публикует всё, что он успел положить в кольца до запроса. Потребитель, увидев запрос, сначала дотягивает кольца, затем вызывает `sink.flush()`, сохраняет код ошибки и публикует `drained` с release. Вызывающий acquire-читает `drained` и спит по 200 мкс между проверками; если потребитель мёртв или завис, есть аварийный выход по бюджету итераций. Смысл барьера: «всё, что было принято до вызова, уже на диске» — а не «всё, что было вызвано, когда-либо будет записано».

При остановке рабочий поток дотягивает всё, что осталось в кольцах, делает финальный flush, публикует последовательность и останавливает сток. `std::jthread` объявлен последним членом, поэтому уничтожается первым: join происходит до того, как умрут продюсер и сток.

## Уровни: одно relaxed-чтение

`core::LogLevel` — это `Verbose`, `Debug`, `Info`, `Warning`, `Error`, `Fatal`, `Off`. Порядок объявления и есть порядок важности (`Verbose < Debug < ... < Fatal < Off`), поэтому фильтр — обычное сравнение, а `Off` как старшее значение делает «выключено всё» верхней границей диапазона, а не отдельным случаем. Под ним `std::uint8_t`: уровень занимает один байт в записи и помещается в lock-free атомик.

Порог живёт в `detail::LevelControl` — одном атомике на собственной 64-байтовой кэш-линии. Чтение — relaxed load, запись — relaxed store. Relaxed здесь не небрежность, а следствие модели памяти: записи самодостаточны, уровень — независимый скаляр, и нет других данных, видимость которых нужно было бы упорядочивать вместе с порогом. Поток, который несколько инструкций действует по старому порогу, просто отфильтровал или пропустил запись так, как это сделал бы старый порог; это допустимо и стоит ровно один load.

`set_level()` можно вызывать из любого потока. Это наблюдение, а не синхронизация: следующий вызов увидит новое значение, но никто не обещает линейного порядка с другими операциями. Для диагностики и управления этого достаточно.

Композитный логгер хранит собственный порог и при `set_level()` проталкивает его во все стоки. При этом у каждого стока остаётся свой фильтр: если файловый сток подняли до `Warning` через `get<FileLogger>()`, композит на `Info` не заставит его писать info. Композит сначала короткозамыкается на своём уровне, затем раздаёт запись каждому члену, а тот применяет свой.

## Анти-спам: две ступени, которые надо включить

В `detail::Producer` есть двухступенчатая защита от шума, но по умолчанию она выключена: продюсер конструирует `SpamProtection` с `enable_repeat_suppression = false` и `max_messages_per_sec_per_shard = 0`. Поля `SpamProtectionConfig` по умолчанию выглядят иначе (`true`, 1000 мс, 100000/с, bypass `Fatal`), но это словарь конфигурации, а не стартовое состояние движка.

Первая ступень — подавление повторов. Хэш идентичности сообщения строится из `source_location`, указателя на формат и упакованных аргументов. Если следующий вызов совпал с предыдущим, он не пишется; счётчик повторов растёт. Когда сообщение меняется или истекает окно, подавление сбрасывается, и вызывающий получает возможность выдать сводку. Хэш — FNV-подобная цепочка, которая стоит около 70 нс, поэтому она считается только при включённом подавлении: при выключенном флаге горячий путь не платит за неё вообще.

Вторая ступень — token bucket на шард с окном в одну секунду. Записи на уровне `bypass_min_level` проходят всегда; исчерпание квоты инкрементирует `throttled_count` в состоянии шарда и отбрасывает запись.

Обновление квот на ходу сделано по-честному: каждое потребляемое поле — отдельный relaxed-атомик, `set_config()` пишет поля по одному. Продюсер, читающий поле, видит целое старое или целое новое значение, но не байтовый разрыв. Линеаризуемого снимка всех полей нет, и это задокументировано как per-field consistency, а не как «wait-free reconfiguration».

Но вот граница, которую важно назвать: публичные логгеры не пробрасывают `set_spam_protection_config()`. У `FileLogger`, `ConsoleLogger` и `Iceoryx2Logger` такого метода нет; включить двухступенчатый анти-спам можно только через внутренний `detail::Producer` (так делают тесты). Настройки при этом доходят до логгера иначе: `apply_to(Settings, FileLoggerConfig&)` берёт `spam_protection.max_messages_per_sec_per_shard` и превращает его в `ThrottleConfig` с окном в одну секунду. То есть в файловом стоке работает не token bucket, а оконный throttle, и его дропы считаются как `rate_limited`; у iceoryx2-стока throttle задаётся напрямую в его конфиге и по умолчанию выключен. `enable_repeat_suppression`, `repeat_suppression_window_ms` и `bypass_min_level` из `logging.json` до горячего пути не доезжают.

## Куда уходят записи

Сток — это холодная сторона. Он получает уже отрендеренную запись и делает с ней что-то наблюдаемое: пишет в fd, в файл, в shared memory или никуда. Контракт duck-typed: `start()`, `on_event(record)`, `flush()`, `stop()`. Общая форма для модулей, которые хотят принимать записи, выражена в `core::concepts::Sink`/`LifecycleSink`: `on_event` и `flush` возвращают `core::Status` и помечены `noexcept`, `start` возвращает `Status`, `stop` ничего не возвращает.

Сток конструируется на месте рабочим потоком при `start()`, поэтому всё его хранилище фиксировано и резидентно до первой записи. Продюсер до стока не дотягивается никогда.

### Консоль

`ConsoleSink` рендерит отложенный формат в scratch на 256 байт, собирает plain-строку в буфере на 512 байт и пишет её сырым `::write` в fd 1 или fd 2. Формат строки:

```text
<монотонные секунды>.<наносекунды> <level> <basename>:<line> (<function>) <message>
```

Важно, что время здесь монотонное, а не UTC: консоль не пытается быть журналом для корреляции с внешним миром, она показывает порядок и относительное время. `Info` и ниже идут в stdout, `Warning` и выше — в stderr. Частичные записи и `EINTR` обрабатываются циклом; закрытый tty или другая ошибка просто прекращают запись — это потеря на стороне потребителя, которая не возвращается продюсеру. `flush()` у консоли — no-op: `write` уже сделан, fsync-цели нет.

### Файл

`FileSink` — основной per-process сток. Он конвертирует монотонную метку в UTC через `TimeBaseClock`, при необходимости переключает период и сегмент, рендерит сообщение в scratch на 512 байт и собирает строгую JSON-строку в буфере на 4096 байт. Схема и порядок полей фиксированы:

```json
{"timestamp":"2026-11-21T14:30:00.123456789Z","mono_ns":123456789,"boot":"0123456789abcdef","level":"warning","app":"controller","thread_id":42,"message":"[control.cpp:87] (run) calibration lost"}
```

Если калибровка времени не покрывает момент записи, `timestamp` становится литералом `null`, а `mono_ns` и `boot` остаются авторитетными. `message` декорируется как `[basename:line] (function) <текст>`; функция пишется ровно так, как её отдаёт `std::source_location`, без демаглинга. Экранирование — общее с `core::FixedWriter`: кавычки и обратный слэш, короткие формы для `\b\t\n\f\r`, `\u00XX` для остальных управляющих байтов, UTF-8 проходит как есть.

Ротация — каталогами по UTC-границам. `RotationSchedule::Hourly` даёт подкаталог `YYYY-MM-DDTHH`, `Daily` — `YYYY-MM-DD`, `Custom` — `epoch-<n>` по эпохо-привязанным окнам, `None` — плоско, без подкаталога. Внутри периода файл называется как задано (`app.jsonl` по умолчанию). Размерная ротация включается `max_file_size_bytes`: при переходе через порог открывается следующий сегмент `<stem>.<n><ext>` (`app.1.jsonl`, `app.2.jsonl`, …). Порядок «открыть новый, потом закрыть старый» соблюдается и для каталогов, и для сегментов: неудачное открытие оставляет живым предыдущий дескриптор, поэтому строка не теряется из-за сбоя ротации. Размер существующего файла учитывается при старте, так что предзаполненный файл не обнуляет бюджет.

Строка, которая не влезла в 4096 байт, не пишется наполовину: она пропускается и учитывается во внутреннем счётчике `malformed_`, а не разрывается на две. `flush()` пересэмплирует UTC-смещение, делает `fsync` активного дескриптора и возвращает накопленную ошибку записи, если она была.

### Shared memory: LogFrame

`Iceoryx2Sink` не пишет файл. Он рендерит сообщение прямо в `payload` фиксированного `LogFrame` и публикует кадр в iceoryx2 pub/sub, после чего уведомляет парный event-сервис.

`LogFrame` — 256 байт, `alignas(64)`, pointer-free и trivially copyable: 31 байт заголовка и `payload[225]`. Именно pointer-free делает возможной zero-copy передачу через shared memory: кадр можно `memcpy`-нуть в разделяемую память и обратно без сериализации. Поля: монотонный `timestamp_ns`, четырёхбайтовый `app_id`, зарезервированный `context_id`, `thread_id`, `pid`, `dropped_counter` (дельта с предыдущего кадра), `payload_size`, `log_level` и сам payload.

Публикация — один вызов `send_copy(frame, header)`: loan, copy, send. Неудачная публикация отбрасывает кадр и не блокирует (`DiscardData`); уведомление event-сервиса best-effort. Публикация работает и с нулём подписчиков — это важно для случаев, когда демон ещё не поднялся.

`dropped_counter` — дельта накопленных дропов с предыдущего кадра, насыщающаяся до `UINT32_MAX`. Она позволяет демону видеть потери без side-band канала. `context_id` пока всегда 0: per-context пороги зарезервированы, но не реализованы.

В кадре нет `file`, `line` и `function`: payload — только текст сообщения. Это осознанный размен ради 256 байт. Локация вызова остаётся в per-process файловом стоке, но не переживает переход в демон.

### Composite и Null

`CompositeLogger<Loggers...>` — fan-out без виртуальных вызовов. Члены лежат в `std::tuple`, все операции разворачиваются fold-выражениями, поэтому каждый вызов статически разрешается и инлайнится. Композит сам удовлетворяет концепту логгера, поэтому композиты вкладываются свободно. `set_level()` пишет собственный порог и проталкивает его во всех членов; `log()` сначала короткозамыкается на своём уровне, затем раздаёт запись каждому; `flush()` флашит всех и возвращает первую ошибку, не маскируя её более поздним успехом. Пустой `CompositeLogger<>` — валидный молчаливый логгер.

`NullLogger` — нулевой сток. Он сохраняет полную форму вызова, включая compile-time проверку формата, но не делает ничего: ни уровня, ни кольца, ни часов, ни рендера. При `-O1` и выше вызов с отброшенным результатом не оставляет в коде ничего. Уровень у него всё же есть — чтобы композит мог единообразно перенастраивать всё дерево.

Сводка по стокам:

| Сток | Куда | Формат | Доступность | Что при переполнении |
|---|---|---|---|---|
| `ConsoleSink` | fd 1 / fd 2 | plain-строка | всегда | нет обратного давления; ошибка записи теряется |
| `FileSink` | JSONL-файл | строгая JSON-строка | всегда | дроп на кольце, строка не пишется наполовину |
| `Iceoryx2Sink` | shared memory | `LogFrame` 256 Б | `NEXIGEN_ENABLE_COM=ON` | публикация отбрасывается, кадр не блокирует |
| `CompositeLogger` | члены | как у членов | всегда | как у членов |
| `NullLogger` | никуда | — | всегда | нечего терять |

## Демон, который собирает всё в один поток

`nexigen-logd` — отдельный процесс, а не библиотечный класс. Он подписывается на сервис `Nexigen/Log/nexigen` (имя настраивается), ждёт кадры через `WaitSet` и event-listener, фильтрует их по `min_log_level_storage` и складывает в буфер на 64 КиБ. Буфер сбрасывается при заполнении половины и по таймеру `batch_flush_interval_ms`, а при `SIGTERM` — досрочно, с `fsync`.

Файлы раскладываются по часовым каталогам UTC:

```text
<log_directory>/2026-11-21T14/nexigen.jsonl
```

Один файл на все приложения: приложение различается полем `"app"`. Строка, которую пишет демон, похожа на файловую, но не идентична:

```json
{"timestamp":"2026-11-21T14:30:00.123456789Z","mono_ns":123456789,"boot":"0123456789abcdef","app":"RECV","level":"info","thread_id":42,"pid":1234,"message":"calibration lost"}
```

Отличия: есть `pid`, нет локации вызова, и `message` — это голый payload кадра. UTC берётся из `TimeBaseClock`, если демон смог прикрепиться к `/nexigen-timebase`; иначе используется однократно сэмплированный offset монотонных часов. При отсутствии обоих `timestamp` становится `null`.

Конфиг демона несёт `service_name`, `log_directory`, `max_file_size_mb`, `max_archive_files`, `min_log_level_storage` (по умолчанию `Warning`), `batch_flush_interval_ms` и спецификацию главного потока. Важная деталь для честной картины: в текущем `tools/nexigen-logd/main.cpp` поля `max_file_size_mb` и `max_archive_files` не читаются — ротация только часовая. Размерная ротация и архивы остаются обещанием конфигурации, а не поведением кода.

Демон доступен только в COM-сборке: `nexigen_logging_com` — интерфейсная цель, которая линкует `nexigen_logging` и `nexigen_com`. Ядро `nexigen_logging` при этом остаётся свободным от iceoryx2.

## Контракт отказов

Логгер интересен не тем, что он пишет, а тем, что он делает, когда писать некуда. Здесь причин больше, чем кажется по публичному `DroppedStats`.

Первая — `buffer_full`: `try_push` в кольцо шарда не удался. Это единственный отказ, который видит продюсер в установившемся режиме.

Вторая — `slot_exhausted`: у потока нет свободного слота в пуле. Счётчик глобальный и кумулятивный: он не сбрасывается при синтезе сводки, потому что описывает исчерпание пула, а не конкретное окно.

Третья — `rate_limited`: исчерпан оконный бюджет `ThrottleConfig`. Именно этот механизм стоит за `spam_protection.max_messages_per_sec_per_shard` в настройках: `apply_to` превращает число в секундное окно throttle. Счётчик живёт в состоянии шарда.

Четвёртая — `throttled`: исчерпана секундная квота `SpamProtection`. Она появляется, только если двухступенчатый анти-спам включён напрямую через `detail::Producer::set_spam_protection_config()`; публичные логгеры этого не делают. Счётчик живёт в `SpamShardState::throttled_count` и попадает в синтезированную сводку, но не входит в `DroppedStats`, у которого ровно три поля: `rate_limited`, `buffer_full`, `slot_exhausted`.

`dropped()` возвращает `DroppedStats` — relaxed-снимок по всем шардам плюс глобальный счётчик исчерпания. Это наблюдение, а не линеаризуемый итог: значения могут относиться к разным эпохам, но каждое отдельное поле — целое значение. Читать можно с любого потока.

Чтобы потери не были молчаливыми, продюсер и потребитель синтезируют диагностическую запись. Она собирается как обычный `LogRecord` уровня `Warning` с текстом вида:

```text
Dropped 17 record(s) in the last window (rate-limited: 2, buffer-full: 9, slot-exhausted: 4, throttled: 2).
```

Продюсер вставляет такую сводку на границе окна throttle — то есть только когда throttle включён. Если throttle выключен (обычный случай), продюсер сводок не генерирует; потребитель синтезирует одну сводку при `flush()`: обходит шарды и отдаёт её прямо в сток, минуя кольца. Счётчики сбрасываются только после успешной вставки или доставки; при неудаче они сохраняются и сводка повторяется позже. Глобальный `slot_exhausted` не сбрасывается.

Что здесь важно для проектирования: дроп — окончательный. Нет дискового буфера, нет повторной попытки, нет backpressure на продюсера. В реальном времени это правильный выбор: лучше потерять строку и посчитать её, чем заблокировать поток управления. Но это значит, что «логгер ничего не потерял» нельзя утверждать без проверки `dropped()` и сводок.

`OverflowPolicy` в конфигурации обещает два режима — `DropNewest` и `OverwriteOldest`, — но текущий `Producer::emit` реализует только первый: полное кольцо всегда даёт `buffer_full` и дроп входящей записи. `OverwriteOldest` существует как словарь и JSON-поле, но горячий путь его не читает. Это ещё одна граница, которую лучше знать заранее.

## `flush()`: что именно обещает барьер

`flush()` — единственный метод, который может блокироваться, и это нормально: он относится к control plane. Его обещание узкое и точное: все записи, принятые до вызова, дошли до стока и синхронизированы. Для файла это означает `fsync`; для консоли — что `write` уже произошёл; для iceoryx2 — что кадры опубликованы. Для записей, которые будут приняты после вызова, никаких гарантий нет.

Handshake устроен так, чтобы не будить потребителя без нужды. Если кольца пусты в момент запроса, потребитель отвечает сразу. Если нет — сначала дотягивает батч, затем флашит сток, сохраняет код ошибки и публикует `drained`. Ошибка стока (например, `SystemError` от неудачного `fsync`) доходит до вызывающего; успех более позднего стока не маскирует более раннюю ошибку.

При уничтожении логгера `std::jthread` делает stop request и join, а `run_loop` перед выходом дотягивает всё, что осталось, флашит и останавливает сток. Поэтому «уничтожение не теряет принятые записи» — это свойство порядка членов и финального дрейн-а, а не удача.

Отдельно стоит сказать про `sync_flush_on_critical`: поле есть в `LoggerOptions` и в JSON, но текущие логгеры его не читают. Автоматического синхронного flush на `Fatal` сегодня нет; если он нужен, его надо вызывать явно.

## Конфигурация: три уровня и один загрузчик

У каждого логгера свой холодный конфиг. `FileLoggerConfig` несёт `app_name`, `base_dir`, `file_name`, `initial_level`, `throttle`, `rotation`, `worker_thread`, `max_file_size_bytes` и `worker_poll_interval_us`. `ConsoleLoggerConfig` — только уровень, worker spec и poll ceiling. `Iceoryx2LoggerConfig` — имя сервиса, четырёхбайтовый `app_id`, лимиты подписчиков и истории, уровень, throttle, worker spec. `LogDaemonConfig` — своё.

Над этим стоит `LoggerOptions` — единый агрегат, из которого настройки маппятся в конкретный конфиг:

| Поле | Значение по умолчанию |
|---|---|
| `log_root_directory` | `"./logs"` |
| `initial_log_level` | `Info` |
| `max_file_size_bytes` | 104857600 (100 МиБ) |
| `spsc_ring_buffer_capacity` | 65536 |
| `message_capacity` | 128 |
| `max_producer_threads` | 64 |
| `overflow_policy` | `DropNewest` |
| `worker_thread` | пустой spec (наследуется) |
| `worker_poll_interval_us` | 1000 |
| `sync_flush_on_critical` | `true` |
| `spam_protection` | 1000 мс, 100000/с, bypass `Fatal`; в файловый сток уходит только пер/сек, как throttle |

Загрузчик `load_logging_settings` читает явно заданные global- и local-файлы, затем применяет переменные окружения. Приоритет: значения по умолчанию → global JSON → local JSON → env. Поле, отсутствующее в источнике с более высоким приоритетом, наследует значение из нижнего. Ошибка в поле не роняет загрузку: она превращается в `SettingsDiagnostic`, а поле сохраняет предыдущее значение — логгер можно инициализировать даже с частично битым конфигом. Загрузчик сам никогда не пишет в лог: логгера ещё нет.

Переменные окружения: `NEXIGEN_LOG_LEVEL`, `NEXIGEN_LOG_DIR`, `NEXIGEN_LOG_MAX_FILE_SIZE_BYTES`, `NEXIGEN_LOG_CPU_AFFINITY`, `NEXIGEN_LOG_RING_CAPACITY`, `NEXIGEN_LOG_MESSAGE_CAPACITY`, `NEXIGEN_LOG_MAX_PRODUCER_THREADS`, `NEXIGEN_LOG_OVERFLOW_POLICY`. Невалидное значение — диагностика и сохранение прежнего значения.

Ёмкости проверяются отдельно: `check_capacity<ShardCapacity, MaxThreads, MessageCapacity>(settings)` сравнивает явно заданные значения с compile-time лимитами конкретной инстанциации. Если конфиг просит больше, инициализация возвращает `InvalidArgument`, а не молча обрезает. Это важно, потому что `LoggerOptions` описывает движок, а не конкретный тип логгера: одна и та же настройка может быть валидной для `FileLogger<1024, 256, 64>` и невалидной для `FileLogger<>`.

Имя приложения в `logging::Settings` не входит: `app_name` — это поле app-уровня (`app::Settings`), которое политика приложения передаёт в `FileLoggerConfig` или `Iceoryx2LoggerConfig` при эмплейсе. Поэтому один и тот же logging.json можно переиспользовать для разных приложений, не переписывая имя.

## Интеграция в приложение

`nexigen::app::Infrastructure` — это heap-only сервис, который собирает логирование, метрики и трейсинг по политике. Политика — stateless-тип с тремя статическими хуками; для логгера это `emplace_logger(out, logging_settings, app_name)`.

Порядок инициализации жёсткий: сначала прикрепляется time base, потому что без него файловый сток не получит UTC; затем создаётся логгер; только после этого — провайдеры метрик и трейсинга. Причина простая: всё, что стартует позже, должно уже иметь куда жаловаться. Если шаг падает, инфраструктура откатывает уже созданные компоненты и возвращает ошибку. `logger()` отдаёт ссылку на собранный логгер; ссылка живёт, пока жива инфраструктура.

Политика решает, куда писать. В `examples/app/ex_app_cli_settings.cpp` и `examples/suite/ex_suite_app.cpp` это `FileLogger<>` с `RotationSchedule::None`: один `<log_root_directory>/app.jsonl`, без часовых подкаталогов. В `examples/integration/suite_2_apps/` — `Iceoryx2Logger<>` с `app_id` из четырёх символов (`"RECV"`, `"GENR"`), а демон собирает кадры в общий `logs/`.

У Execution Manager своя, независимая от приложения, файловая ветка. `nexigen::exec` поднимает `FileLogger<64, 256, 4>` и пишет `execution_manager.jsonl` в каталог артефактов; если основной путь недоступен, пробует `<cwd>/.nexigen-exec`; если и это не вышло, диагностика уходит в stderr. Перед каждым `fork` после инициализации логгер приостанавливается и join-ится, а в родителе создаётся заново — иначе worker-поток пережил бы fork. Этот логгер не пересекается с логгером приложения и имеет собственные настройки и жизненный цикл.

`nexigen-hub` логи не пишет: он читает артефакты (`app.jsonl`, `execution_manager.jsonl` и другие) и строит по ним наблюдаемую картину. Поэтому путь и схема файлов — часть контракта, а не деталь реализации.

## Полный пример: `main` с файловой политикой

Ниже — полный исходник `examples/app/ex_logging_file_policy.cpp`. Он собран и запущен в этом дереве: один `main`, политика с `FileLogger<>`, плоский файл `app.jsonl`, второй поток-продюсер, явный `flush()`, проверка `dropped()` и `shutdown()`.

Сборка и запуск:

```bash
cmake --build build-com -j 64 --target ex_logging_file_policy
mkdir -p /tmp/nexigen-logging && cd /tmp/nexigen-logging
/path/to/build-com/examples/app/ex_logging_file_policy
```

```cpp
// nexigen::app — runnable file-logging example.
//
// One main() creates a heap-only Infrastructure with a FileLogger policy,
// writes a flat JSONL file, exercises a second producer thread, flushes and
// verifies the produced file. The time base is the in-process fixture used by
// the other app examples; production applications attach to nexigen-chronod.
//
// Run from a build tree:
//   cmake --build build-com -j 64 --target ex_logging_file_policy
//   ./build-com/examples/app/ex_logging_file_policy
// Output:
//   ./nexigen-logging-example/app.jsonl
#include <cstddef>
#include <cstdint>
#include <cstdio>
#include <fstream>
#include <memory>
#include <optional>
#include <string>
#include <string_view>
#include <thread>
#include <utility>

#include <nexigen/app/infrastructure.hpp>
#include <nexigen/chrono/null_sink.hpp>
#include <nexigen/core/log_level.hpp>
#include <nexigen/core/result.hpp>
#include <nexigen/logging/file_logger.hpp>
#include <nexigen/logging/settings.hpp>
#include <nexigen/metrics/null_metric_sink.hpp>
#include <nexigen/tracing/null_trace_sink.hpp>

#include "time_base_fixture.hpp"

namespace {

namespace app = nexigen::app;
namespace core = nexigen::core;
namespace logging = nexigen::logging;
namespace metrics = nexigen::metrics;
namespace tracing = nexigen::tracing;

constexpr std::string_view kOutputDir = "./nexigen-logging-example";

/// Stateless policy: one FileLogger, flat directory, no rotation.
///
/// The metrics and tracing sinks are null on purpose: this example is about
/// logging, and the Infrastructure still requires all three components.
struct FilePolicy {
    using Logger = logging::FileLogger<>;
    using MetricsSink = metrics::NullMetricSink;
    using TraceSink = tracing::NullTraceSink;

    static core::Status emplace_logger(std::optional<Logger>& out,
                                       const logging::Settings& settings,
                                       std::string_view app_name) noexcept {
        const core::Status capacity =
            logging::check_capacity<Logger::capacity(), Logger::max_threads(), 128>(settings);
        if (!capacity) {
            return capacity;
        }
        logging::FileLoggerConfig cfg{};
        const core::Status applied = logging::apply_to(settings, cfg);
        if (!applied) {
            return applied;
        }
        cfg.app_name = std::string(app_name);
        cfg.rotation.kind = logging::RotationSchedule::None;
        out.emplace();
        return out->initialize(cfg);
    }

    static core::Status emplace_metrics_sink(std::optional<MetricsSink>& out,
                                             const metrics::Settings&, std::string_view) noexcept {
        out.emplace();
        return {};
    }

    static core::Status emplace_trace_sink(std::optional<TraceSink>& out, const tracing::Settings&,
                                           std::string_view) noexcept {
        out.emplace();
        return {};
    }
};

int fail(std::string_view message) {
    std::fprintf(stderr, "ex_logging_file_policy: %.*s\n", static_cast<int>(message.size()),
                 message.data());
    return 1;
}

std::size_t count_lines(const std::string& path) {
    std::ifstream in{path};
    std::size_t lines = 0;
    for (std::string line; std::getline(in, line);) {
        if (!line.empty()) {
            ++lines;
        }
    }
    return lines;
}

} // namespace

int main() {
    nexigen::examples::LocalTimeBase time_base{"logging-file"};
    if (!time_base.is_open()) {
        return fail("local time base could not be created");
    }

    auto created = app::make_infrastructure<FilePolicy, 256, 8>();
    if (!created.has_value()) {
        return fail("make_infrastructure failed");
    }
    auto infra = std::move(*created);

    app::Settings settings = app::Settings::create("logging-example");
    settings.logging.options.log_root_directory = std::string(kOutputDir);
    settings.logging.options.initial_log_level = core::LogLevel::Debug;
    settings.logging.options.max_file_size_bytes = 0;
    settings.chrono.segment_name = time_base.name();

    const core::Status initialized = infra->initialize(settings);
    if (!initialized) {
        return fail("Infrastructure::initialize failed");
    }

    infra->logger().info("infrastructure ready: app={}", std::string_view{"logging-example"});
    infra->logger().debug("debug detail: shard={}", 0);
    infra->logger().warning("warning goes to the file too");

    std::thread producer(
        [&infra] { infra->logger().info("record from a second producer thread"); });
    producer.join();

    std::uint32_t ticks = 0;
    const app::InfrastructureStopReason reason = infra->run([&] {
        infra->logger().info("tick {}", ++ticks);
        if (ticks == 3) {
            infra->request_stop(app::InfrastructureStopReason::Requested);
        }
    });
    if (reason != app::InfrastructureStopReason::Requested) {
        return fail("run() did not return Requested");
    }

    const core::Status flushed = infra->logger().flush();
    if (!flushed) {
        return fail("logger flush failed");
    }
    const logging::DroppedStats dropped = infra->logger().dropped();

    const core::Status shutdown = infra->shutdown();
    if (!shutdown) {
        return fail("Infrastructure::shutdown failed");
    }

    const std::string path = std::string(kOutputDir) + "/app.jsonl";
    const std::size_t lines = count_lines(path);
    std::printf("ex_logging_file_policy: OK (ticks=%u, lines=%zu, dropped=%llu, file=%s)\n", ticks,
                lines, static_cast<unsigned long long>(dropped.total()), path.c_str());
    return lines >= 6 ? 0 : 1;
}
```

Что здесь важно:

- **Политика — единственное место, где выбирается сток.** `using Logger = FileLogger<>` и `emplace_logger` — это и есть ответ на вопрос «куда писать». Метрики и трейсинг здесь нулевые: `Infrastructure` требует все три компонента, но пример про логирование.
- **`check_capacity`** сравнивает явно заданные ёмкости из настроек с compile-time лимитами `FileLogger<>`. Если конфиг просит больше, чем есть у инстанциации, инициализация вернёт `InvalidArgument`, а не обрежет молча.
- **`apply_to`** переносит `LoggerOptions` в `FileLoggerConfig`: `base_dir`, уровень, размерный лимит, worker spec, poll interval. Имя приложения и режим ротации пример задаёт сам: `app_name` — app-level, `RotationSchedule::None` — плоский файл.
- **`time_base_fixture.hpp`** — только для примеров. В проде приложение прикрепляется к `nexigen-chronod` через `settings.chrono.segment_name`; без time base файловый сток оставит `timestamp` в JSON равным `null`, а `mono_ns` и `boot` — авторитетными.
- **Второй поток** — не декорация: он клеймит второй шард и проходит тот же горячий путь. В выводе его запись может стоять ниже тиков, хотя её `timestamp` раньше: файл пишется в порядке дрейн-а, а не в порядке глобальной сортировки.
- **`flush()` вызывается явно** до `shutdown()`; `shutdown()` всё равно флашит, но пример показывает оба шага. `dropped()` читается как снимок: `dropped=0` означает «на момент чтения счётчики нулевые», а не «за всё время ничего не потеряно».
- **Проверка в конце** считает строки в файле: `lines >= 6` — грубый, но полезный smoke-тест, что записи действительно дошли до диска.

Фактический вывод на этой машине:

```text
ex_logging_file_policy: OK (ticks=3, lines=8, dropped=0, file=./nexigen-logging-example/app.jsonl)
```

Одна строка из полученного `app.jsonl`:

```json
{"timestamp":"2026-11-21T08:04:23.639584784Z","mono_ns":57718333786199,"boot":"0397e3b78a374af3","level":"info","app":"logging-example","thread_id":526371,"message":"[ex_logging_file_policy.cpp:128] (int main()) infrastructure ready: app=logging-example"}
```

Восемь строк — это три стартовых сообщения, запись из второго потока, три тика и финальная строка `shutdown reason: requested`, которую `Infrastructure` пишет сам. Её локация — `infrastructure.hpp`, а не пользовательский код: это видно по полю `message`.

## Диагностика

Почти каждый публичный тип подсистемы имеет `to_string()` и `std::formatter`: конфиги, `LogRecord`, `DroppedStats`, `SpamProtection`, `LogFrame`, уровни, enum'ы. Это холодный путь, но именно он позволяет дебажить без специального инструмента.

У асинхронных логгеров есть снимки, безопасные с третьего потока: `dropped()` — по причинам, `pending()` — сколько записей ещё ждёт потребителя, `writer_started()` — дошёл ли worker до цикла, `writer_start_code()` — первая ошибка старта, `writer_thread_report()` — что именно применилось из thread spec, `writer_mask()` — фактическая маска CPU. Всё это наблюдения, а не синхронизация: `pending()` может устареть через наносекунду, и это нормально.

`LevelControl` — тоже снимок: `level()` возвращает то, что видит вызывающий поток, а не глобально линейный порядок. Для диагностики этого достаточно; для протокола — нет, и подсистема не притворяется, что даёт больше.

У `nexigen::exec` есть `execution_manager_logging_path()` и `execution_manager_logging_active()`: путь и факт активности файловой ветки. Это удобно для сообщений «логи здесь» и для тестов, которые проверяют, что логгер действительно поднялся.

## Границы

Подсистема большая, но не всемогущая. Полезно перечислить, чего в ней сегодня нет — чтобы не искать это в коде.

- **Нет syslog/journald/network-стока.** Есть консоль, файл и shared memory до демона. Если нужен journald, его надо писать отдельным стоком.
- **Демон не библиотека.** `nexigen-logd` — утилита; встроить его в процесс нельзя.
- **`OverflowPolicy::OverwriteOldest` не реализован** в горячем пути: полное кольцо всегда даёт `buffer_full` и дроп входящей записи.
- **`sync_flush_on_critical` не потребляется** логгерами: автоматического flush на `Fatal` нет.
- **Двухступенчатый анти-спам не подключён к публичным логгерам**: `enable_repeat_suppression`, `repeat_suppression_window_ms` и `bypass_min_level` из настроек не применяются; `set_spam_protection_config()` есть только у внутреннего `Producer`.
- **Размерная ротация демона не подключена**: `max_file_size_mb` и `max_archive_files` в конфиге есть, в `main.cpp` не читаются.
- **Демон теряет локацию вызова** и не пишет `dropped_counter` в строку, хотя кадр его несёт.
- **`LogFrame` payload — 225 байт**, `app_id` — 4 байта; длинное сообщение усечётся.
- **`std::string_view` усекается до `MessageCapacity / 2`**; флаг усечения есть, но текст уже потерян.
- **`context_id` зарезервирован**, per-context пороги не реализованы.
- **`flush()` блокирует** и не предназначен для горячего пути.
- **`CompositeLogger` статичен**: набор стоков фиксирован типом, динамического списка нет.
- **`Iceoryx2Logger` только в COM-сборке**; ядро `nexigen_logging` от iceoryx2 не зависит.
- **`logging::Settings` не содержит `app_name`**: имя приложения — app-level.

## Сводка

```text
                     +---------------------------------------------+
  logger.info(...)   |  Producer (горячий путь, ≤ 20 нс)           |
  ------------------>|  level -> slot -> tid -> stamp -> throttle  |
                     |  -> pack -> spam -> try_push                |
                     +----------------------+----------------------+
                                            |
                     +----------------------v----------------------+
                     |  per-thread SPSC shards (MaxThreads)        |
                     +----------------------+----------------------+
                                            |
                     +----------------------v----------------------+
                     |  AsyncWorker (один jthread на логгер)       |
                     |  drain 64/батч, render, sink.on_event       |
                     +---+------------------+------------------+---+
                         |                  |                  |
                    ConsoleSink         FileSink          Iceoryx2Sink
                    fd 1 / fd 2         JSONL + ротация   LogFrame 256 Б
                         |                  |                  |
                    терминал           <base>/<label>/     nexigen-logd
                                        app.jsonl          <log_dir>/<hour>/
                                                            nexigen.jsonl
```

Система держится на трёх решениях. Продюсер не форматирует и не блокируется — он пакует запись и кладёт её в своё кольцо. Потребитель один на логгер, он рендерит, пишет и отвечает за `flush()`. Сток — сменная холодная сторона, поэтому консоль, файл, shared memory, композит и null используют один и тот же горячий путь.

Цена этой схемы — фиксированные ёмкости, окончательные дропы и честные счётчики. Взамен вызывающий поток платит за логгер десятки наносекунд и никогда не ждёт диск, демона или форматтер. Для системы реального времени это правильный размен; для системы, которой нужен «лог, который точно ничего не потеряет», — повод посмотреть на `dropped()` и добавить внешний сборщик.
