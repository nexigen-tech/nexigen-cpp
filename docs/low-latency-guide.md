# Минимальные задержки: пошаговое руководство

Практическое руководство по снижению задержки «публикация → обработка» в приложениях
на `nexigen`. Все числа получены на демонстрационном стенде
`examples/integration/simulation_suite` (AMD Ryzen Threadripper 9970X, 32 ядра /
64 потока, Linux, iceoryx2, вектор раз в секунду). Каждый шаг указывает, что именно
измерялось и в какой сборке, чтобы цифры нельзя было перепутать.

Порядок шагов — это и есть порядок рычагов: сначала то, что даёт в разы и ничего не
стоит, потом то, что стоит ядра или прав. Не переставляйте их местами: настройка
`SCHED_FIFO` на Debug-сборке с опросом не даст ничего заметного.

---

## 0. Сначала договоритесь, что измеряете

«Задержка» в разных контекстах — разные величины. Здесь она определена так:

```
t0  отправитель: непосредственно перед публикацией (до loan/send)
t1  получатель:  сразу после receive(), до трейсинга, логов и printf
latency = t1 - t0
```

Правила, без которых замер врёт:

1. **Метку `t1` ставьте до любой работы получателя.** Если взять её после
   `start_span()` и `set_attribute()`, в число попадёт стоимость трейсинга.
2. **Не включайте в окно печать.** `printf` + `fflush` в файл — это `write(2)`;
   ставьте метку раньше, а печатайте после.
3. **Считайте задержку один раз.** Консольная строка и метрика должны показывать
   одну и ту же величину, иначе вы будете отлаживать расхождение, а не систему.
4. **Раскладывайте на шаги.** Держите отдельные gauge'и: `publish_cost_us`
   (t0 → `send()` вернулся) и `loan_cost_us` (стоимость займа чанка). Без этого
   невозможно понять, что оптимизировать.
5. **Сравнивайте при одинаковой нагрузке.** Фоновый браузер и IDE добавляют
   десятки микросекунд к хвосту.

---

## 1. Собирайте Release, а не Debug (×7)

Самый большой и самый дешёвый шаг.

| Сборка | Задержка end-to-end (spin) |
|---|---|
| Debug | 72–116 µs |
| Release (`-O3 -march=native -flto`) | **8–17 µs** |

Причин две, и обе коварны:

* C++-часть между меткой и публикацией компилируется `-O0`;
* сборка льёт **debug-артефакт Rust** iceoryx2 (`rust/native/debug/...`), а не
  release. Проверить, что слинковано, можно так:

```bash
grep -o '[^ ]*rust/native/[a-z]*/[^ ]*\.a' build-com/build.ninja | head -1
```

```bash
cmake -B build/release -G Ninja -DCMAKE_BUILD_TYPE=Release
cmake --build build/release -j 64
```

Драйвер демонстрации предупреждает, если выбранное дерево не Release — не
игнорируйте это предупреждение при снятии метрик.

---

## 2. Не опрашивайте — просыпайтесь по событию

Опрос с фиксированным периодом добавляет к каждой задержке равномерную случайную
величину из `[0, период)`:

| Способ получения | Задержка (Debug, spin выключен) |
|---|---|
| `sleep_for(50 ms)` + `receive()` | 8–11 ms |
| `WaitSet` + `EventListener` | **~200 µs** |

Схема, которая используется в примере:

```cpp
// отправитель: уведомить после каждой успешной публикации
static_cast<void>(vector_event->notify());   // сервис .../VectorsEvent

// получатель: блокироваться на событии, а не спать
auto waitset = com::WaitSet::create_without_signal_handling();
auto guard   = waitset->attach_notification(listener);
waitset->wait_and_process_once_with_timeout(
    [&](com::WaitSetAttachmentId id) -> com::CallbackProgression {
        if (id.has_event_from(*guard)) {
            static_cast<void>(listener->try_wait([](com::EventId) {}));
            drain();                 // забрать всё, что накопилось
        }
        return com::CallbackProgression::Continue;
    },
    std::chrono::milliseconds(200)); // таймаут — только для проверки состояния
```

Три детали, которые легко упустить:

* **Уведомление — счётчик, а не очередь.** Потерянное событие не теряет данные:
  сэмплы лежат в подписке, и одно пробуждение дренирует всё накопленное.
* **Таймаут WaitSet нужен и при событийном пробуждении** — иначе цикл не увидит
  смену состояния Function Group и запрос остановки.
* **Событие — подсказка, а не источник истины.** Если канал событий недоступен,
  оставляйте откат на опрос: приложение обязано работать и без него.

## 3. Предзаймите чанк — держите `loan` вне горячего пути

Займ слота в разделяемой памяти стоит микросекунды, и если делать его
непосредственно перед публикацией, он попадает в измеряемое окно. Хуже того, после
секунды сна метаданные пула и заголовок слота вымыты из кэша.

| | до предзаёма | после |
|---|---|---|
| `loan_uninit` | 5–13 µs (холодный) | **~3 µs** (горячий, вне окна) |
| end-to-end (Release, spin) | 8–17 µs | **4–8 µs** |

Шаблон: держите один чанк займованным и берите следующий **сразу после** `send`,
пока пул и сегмент горячие.

```cpp
std::optional<com::SampleMutUninit<T, H>> next_loan;
preloan();                                   // до цикла

// в цикле публикации:
auto mut = next_loan->write_payload(sample);
next_loan.reset();
auto header = tracing::make_trace_header(seq++);
mut.user_header_mut() = header;
const auto sent = publisher->send(std::move(mut));
preloan();                                   // следующий заём — здесь
```

Обязательный откат: если пул пуст, `loan_uninit()` вернёт ошибку — тогда
займовайте синхронно в критической секции и публикуйте. Держать займованным больше
одного чанка нельзя: `publisher_max_loaned_samples` по умолчанию равно двум.

## 4. Спин вместо блокировки — если нужен последний рычаг

Блокирующее пробуждение стоит планировщика. Если поток готов сжечь ядро, он может
крутиться на `receive()` и забирать сэмпл в момент появления.

| Режим | Задержка (Debug) | CPU |
|---|---|---|
| `WaitSet` (блокировка) | 173–265 µs | ~0 % |
| spin | **44–120 µs** | **100 % одного ядра** |

```bash
NEXIGEN_SIM_SPIN=1 ./examples/integration/simulation_suite/run_simulation_suite.sh
```

Правила безопасного спина:

* **Ограничивайте срез** (в примере 20 мс) и возвращайтесь в цикл `Infrastructure::run`,
  иначе SIGTERM не будет обработан.
* **Проверяйте дедлайны внутри среза**, а не только на его границе.
* **Не спините в фоновых потоках** — только в одном выделенном потребителе.

## 5. `SCHED_FIFO` — убрать очередь планировщика

Когда поток разбужен, он ещё ждёт, пока планировщик до него дойдёт. Политика
реального времени убирает эту очередь; именно она отвечает за хвост распределения.

```cpp
core::ThreadSpec spec;
static_cast<void>(spec.set_name("sim-rt"));
const core::Status scheduled =
    spec.set_scheduler(core::SchedulingPolicy::FIFO, 50);
core::ThreadApplyReport report;
const core::Status applied = core::apply_thread_spec_self(spec, report);
```

**Ловушка, на которой легко обмануться.** В необязательном режиме
`apply_thread_spec_self` возвращает **успех**, даже если ядро отказало в политике:
отказ виден только в `report.failed()`. Проверяйте отчёт, иначе приложение
залогирует «SCHED_FIFO priority 50», оставаясь на `SCHED_OTHER`:

```cpp
if ((report.failed() & core::ThreadApplyReport::scheduler_mask) != 0U) {
    // политика не применена: логируем предупреждение и продолжаем
}
```

Что нужно на хосте:

```bash
ulimit -r                      # RLIMIT_RTPRIO, должен быть > 0
chrt -f 50 true                # проверка права
echo "$USER  -  rtprio  99" | sudo tee -a /etc/security/limits.conf   # затем перелогин
```

Если приложение запускает `nexigen-exec` от привилегированного пользователя, в
манифесте приложения нужен `"allow_rt_priority": true`, иначе Execution Manager
срежет `CAP_SYS_NICE` у ребёнка. Поле несовместимо с явным `uid`.

На стенде, где готовилось это руководство, `RLIMIT_RTPRIO` равен нулю и capabilities
нет, поэтому измерен только путь деградации: приложение логирует отказ и остаётся на
`SCHED_OTHER`. Ожидаемый эффект — сжатие хвоста распределения, а не сдвиг медианы.

## 6. Проверьте частоту ядра и governor

В простое ядра сбрасывают частоту. На стенде `lscpu` показывал **48 %** от
номинала — это множитель примерно на всё, что вы измеряете.

```bash
lscpu | grep "CPU(s) scaling MHz"
cat /sys/devices/system/cpu/cpu0/cpufreq/scaling_governor
sudo cpupower frequency-set -g performance      # или
echo performance | sudo tee /sys/devices/system/cpu/cpu*/cpufreq/scaling_governor
```

Спин-режим сам по себе удерживает частоту высоко, поэтому пары «spin + powersave» и
«blocking + powersave» могут различаться сильнее, чем ожидается от одного лишь
планировщика.

---

## 7. Уберите нагрузку и изолируйте ядра

Задержка хвоста на рабочей машине — это чаще всего чужая нагрузка, а не ваш код.

* Не запускайте измерения при работающем браузере, IDE и индексаторах.
* Для честных замеров изолируйте ядра: `isolcpus=`, `nohz_full=`, cgroup `cpuset`.
* Не сажайте горячий поток на SMT-соседа того ядра, где работает чужой busy-loop.

## 8. Affinity: что реально проверено

Раскладка «производитель и потребитель на двух потоках одного физического ядра»
(пара SMT) выглядит логично, но на стенде медиану не изменила:

| Раскладка | Медиана (Debug, spin) |
|---|---|
| разные ядра (6-7 / 8-9) | ~235 µs |
| SMT-соседи (6 / 38) | ~231 µs |

Разница в пределах шума. Причина: при блокирующем пробуждении доминирует не
передача кэш-линии, а планировщик; после перехода на спин — уже сам цикл.

Практический вывод: affinity нужен для **предсказуемости** (процесс не мигрирует
между ядрами и не конкурирует с чужими потоками), а не как средство снижения
медианы. Начинайте с разнесения по разным ядрам и не тратьте время на SMT-трюки,
пока не убраны шаги 1–5.

---

## 9. Почему iceoryx2 обещает 90–100 ns, а вы видите микросекунды

Это разные величины. Заявленные 90–100 ns — про **передачу уже займованного чанка**
в горячем цикле: обе стороны крутятся, данные в L1, ни аллокации, ни уведомления.

Ваш end-to-end включает больше:

| Компонент | Время (Release, spin) |
|---|---|
| генерация полезной нагрузки | < 1 µs |
| `loan_uninit` (с предзаёмом) | ~3 µs, вне окна |
| `send` | 2–4 µs |
| видимость + `receive` | 1–3 µs |
| **итого** | **4–8 µs** |

Разрыв с 90 ns объясняется частотой ядра, холодными кэшами после периода ожидания и
доставкой нескольким подписчикам, а не накладными расходами обёртки.

## 11. Чек-лист

- [ ] Сборка Release, в `build.ninja` линкуется `rust/native/release`.
- [ ] Метка получателя стоит сразу после `receive()`.
- [ ] Печать и трейсинг — вне окна измерения.
- [ ] Консоль и метрика показывают одну и ту же задержку.
- [ ] Есть gauge'и `publish_cost_us` и `loan_cost_us`.
- [ ] Получатель просыпается по событию, а не по `sleep_for`.
- [ ] Публикация предзаймована, есть откат при пустом пуле.
- [ ] Спин (если включён) ограничен срезом и уступает stop-запросу.
- [ ] `SCHED_FIFO` проверен через `chrt -p`, а не по строке в логе.
- [ ] Измерения сняты без посторонней нагрузки.

## 12. Как воспроизвести

```bash
# полный стек, Release, событийное пробуждение
BUILD_DIR=build-release-com \
  ./examples/integration/simulation_suite/run_simulation_suite.sh

# + спин
BUILD_DIR=build-release-com NEXIGEN_SIM_SPIN=1 \
  ./examples/integration/simulation_suite/run_simulation_suite.sh

# + RT-политика (нужен rtprio)
BUILD_DIR=build-release-com NEXIGEN_SIM_SPIN=1 NEXIGEN_SIM_RT_PRIORITY=50 \
  ./examples/integration/simulation_suite/run_simulation_suite.sh

# наблюдение
tail -f /tmp/opencode/nexigen-simulation-suite/artifacts/simulation-suite/vector_receiver/1/attempt-0001/stdout.log
curl -s http://127.0.0.1:9101/metrics | grep -E "publish_cost|loan_cost"

# остановка
./examples/integration/simulation_suite/clean_simulation_suite.sh
```
