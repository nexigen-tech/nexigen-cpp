# tracing/span-context Specification

## Purpose

Defines trace and span identifiers with their wait-free thread-local generation, the propagable span context, automatic intra-thread parent tracking, the fixed-size span attribute union, and the cache-line-aligned span record shape.

## Requirements

### Requirement: Trace and span identifier generation

The system SHALL provide `TraceId` and `SpanId` as trivially copyable 64-bit value types generated by a non-zero fast `thread_local` monotonic/xorshift generator: generation never allocates, never locks, and never blocks; identifiers generated on different threads are distinct with overwhelming probability; the all-zero value is reserved as the "unset" sentinel and never returned by the generator.

#### Scenario: Generated identifiers are non-zero and distinct

- **WHEN** identifiers are generated on the creating thread and on 32 concurrently creating threads
- **THEN** no generated `TraceId` or `SpanId` equals zero, and no identifier is generated twice across the threads in the observed window

#### Scenario: Generation is wait-free and allocation-free

- **WHEN** a large batch of identifiers is generated in a loop with the allocation counter armed
- **THEN** every generation completes in bounded steps with no lock, no cross-thread atomic, no heap allocation, and no `std::string` construction

#### Scenario: Identifier construction is value-safe

- **WHEN** a `TraceId` or `SpanId` is default-constructed and compared against one built from an explicit 64-bit value
- **THEN** the default reads as the zero sentinel, explicit values are preserved, and equality/ordering compare the underlying 64-bit counts

### Requirement: Propagable span context

The system SHALL provide `SpanContext` as a lightweight trivially copyable struct holding exactly `TraceId trace_id`, `SpanId span_id`, and `SamplingDecision sampled`, small enough to be passed across threads or through bounded queues to link parent-child spans across thread boundaries, with value equality and a diagnostic `to_string()`.

#### Scenario: Context survives cross-thread handoff unchanged

- **WHEN** a context produced on one thread is copied into a queue, popped on another thread, and compared with the original
- **THEN** the copy compares equal, every field is unchanged, and the type is trivially copyable with `sizeof` no larger than 24 bytes

#### Scenario: Context renders and parses as a diagnostic

- **WHEN** `to_string` is called on a context and the free `to_string(const T&)` mirrors it
- **THEN** both render the trace id, span id, and sampling decision, and `std::format("{}", ctx)` yields the same text

### Requirement: Automatic intra-thread parent tracking

The system SHALL maintain a fixed-depth `thread_local` active-span stack per recording thread: starting a new span automatically inherits the current thread's active `TraceId` and sets the parent span id to the active span's id, unless an explicit parent `SpanContext` is provided; a span started with an empty stack or beyond the documented fixed depth records as a root span with a freshly generated `TraceId` and the zero parent id; the stack never grows dynamically.

#### Scenario: Nested spans chain parent ids

- **WHEN** a span is started while another span is active on the same thread
- **THEN** the child's drained record carries the active span's `TraceId` as its own trace id and the active span's id as `parent_span_id`

#### Scenario: Siblings share the trace id

- **WHEN** two spans are started sequentially inside the same parent on the same thread
- **THEN** both drained records carry the same trace id and the same parent span id

#### Scenario: Explicit parent overrides the stack

- **WHEN** a span is started with an explicit parent `SpanContext` while a different span is active on the thread
- **THEN** the child's trace id and parent span id come from the explicit context, not from the active stack

#### Scenario: Root spans and depth overflow are bounded

- **WHEN** a span is started on a fresh thread with an empty stack, and when spans are nested beyond the documented fixed depth
- **THEN** the fresh-thread span records a new trace id with the zero parent id, the over-deep span also records as a bounded root span, and no dynamic memory is allocated in either case

### Requirement: Fixed-size span attribute union

The system SHALL provide `SpanAttribute` as a fixed-size, trivially copyable tagged union carrying an inline bounded key and one value of `std::int64_t`, `std::uint64_t`, `double`, `bool`, or string, with a type tag that itself follows the enum naming, JSON, and format contract.

#### Scenario: Every value type packs and reads back

- **WHEN** attributes of each supported value type are set on a span and the drained record is inspected
- **THEN** each attribute's key and value survive exactly: integers and unsigned integers, doubles bit-for-bit, booleans, and strings within the inline bound

#### Scenario: Union stays trivially copyable and fixed-size

- **WHEN** `SpanAttribute` is inspected at compile time
- **THEN** it is trivially copyable, `sizeof` it is a compile-time constant independent of the value stored, and its type tag follows the enum serialization contract

### Requirement: Span attribute string storage

A string attribute value that fits the inline string bound SHALL be copied in place; a longer string value SHALL be stored as a zero-copy view whose referenced storage the caller guarantees outlives the span's drain (string literals and program-static tables qualify).

#### Scenario: Short strings copy inline

- **WHEN** an attribute is set with a string value within the inline bound and the drained record is inspected after the source buffer changes
- **THEN** the record still renders the original text from its inline copy

#### Scenario: Long string values are stored as views

- **WHEN** an attribute is set with a string value longer than the inline string bound, backed by storage that outlives the drain
- **THEN** the drained record renders the full string text through the view, and no bytes are copied into the record

### Requirement: Span attribute capacity bounds

A span SHALL carry at most `MaxAttributes` (4) inline attributes; an update beyond that capacity, or with a key longer than the inline key bound, SHALL be rejected without side effects.

#### Scenario: Attribute capacity is bounded

- **WHEN** a fifth attribute is set on a span whose four attribute slots are full
- **THEN** the update is rejected without side effects, no allocation or lock occurs, and the first four attributes are unaffected

#### Scenario: Long keys are rejected

- **WHEN** an attribute is set with a key longer than the inline key bound
- **THEN** the update is rejected without side effects and no partial key is stored

### Requirement: Cache-line-aligned span record

The system SHALL provide `SpanRecord` as a trivially copyable, cache-line-aligned (`alignas(64)`), fixed-size struct containing the trace id, span id, parent span id, `SpanKind`, `SpanStatus`, the cached Linux thread id, start and end monotonic timestamps from `nexigen::chrono`, the `std::source_location`, the inline span name, and the inline attribute array with its count; `sizeof` SHALL be an exact multiple of the cache-line size pinned at compile time.

#### Scenario: Record shape is pinned at compile time

- **WHEN** `SpanRecord` is inspected at compile time
- **THEN** it is trivially copyable, aligned to 64 bytes, and `sizeof` it equals the pinned multiple-of-64 constant

#### Scenario: Records copy losslessly

- **WHEN** a populated record is copied through a byte-for-byte copy and every field of the copy is compared with the original
- **THEN** all fields — ids, parent, kind, status, thread id, both timestamps, location, name, and every attribute — are equal

#### Scenario: Record serialization round-trips

- **WHEN** a populated record is serialized with `to_json` and parsed back with `from_json` under `JSON_NOEXCEPTION=1`
- **THEN** every field survives the round-trip, identifiers render as zero-padded 16-character hexadecimal strings, and `std::format("{}", record)` equals `record.to_string()`

#### Scenario: Hostile JSON leaves the record unchanged

- **WHEN** `from_json` receives a JSON scalar, array, `null`, or an object with wrong-typed fields on a pre-populated record
- **THEN** the call returns normally with no abort under `-fno-exceptions` and the record is unchanged
