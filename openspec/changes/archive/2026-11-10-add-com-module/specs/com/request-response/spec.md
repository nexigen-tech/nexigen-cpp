# Spec Delta

## Purpose

Defines the Request-Response (Method) pattern: `Client<Req,Resp>` sends typed requests to `Server<Req,Resp>` over a correlated bidirectional channel, supporting synchronous calls with timeout and asynchronous pending responses, all through zero-copy shared memory.

## ADDED Requirements

### Requirement: Typed client and server

`nexigen::com::Client<Req,Resp>` and `nexigen::com::Server<Req,Resp>` SHALL carry the request and response types as template parameters constrained by `com::concepts::Message`, and a server SHALL answer exactly the service it was created for.

#### Scenario: Server receives the request and answers

- **WHEN** a client sends a request for a service and the server for that service reads it
- **THEN** the server receives the request payload and its response reaches the waiting client

### Requirement: Correlation of requests

Every request SHALL carry a unique correlation id generated by the client, and the response SHALL carry the same id, so a caller can match an asynchronous reply to its request.

#### Scenario: Response matches its request

- **WHEN** one client issues two outstanding requests and the server answers out of order
- **THEN** each response carries the correlation id of its own request and the caller can pair them correctly

### Requirement: Synchronous call with timeout

The client SHALL offer a synchronous `call()` that blocks the calling thread until the response arrives or a caller-supplied timeout elapses; a timeout SHALL return `com::Error::Timeout` and leave the caller free to ignore or retry.

#### Scenario: Fast server returns in time

- **WHEN** a synchronous call is made against a responsive server
- **THEN** the call returns the server's response before the timeout

#### Scenario: Timeout is reported

- **WHEN** the server does not answer within the timeout
- **THEN** the call returns `Timeout` and no response is delivered afterwards

### Requirement: Asynchronous pending responses

The client SHALL offer an asynchronous send returning a `PendingResponse` handle that the caller polls or awaits later; the caller SHALL NOT be required to block.

#### Scenario: Asynchronous request completes later

- **WHEN** a request is sent asynchronously and the server answers after a delay
- **THEN** the caller retrieves the matching response from the pending handle when it arrives

### Requirement: Method zero-copy and non-POD rejection

Request and response payloads SHALL travel zero-copy like publish-subscribe samples, and a payload type failing `com::concepts::Message` SHALL be rejected at compile time.

#### Scenario: Request payload is zero-copy

- **WHEN** a request with a trivially-copyable payload is sent
- **THEN** the server reads the exact bytes without any serialization step

### Requirement: Method port diagnostics

`Client` and `Server` SHALL provide a cold-path `to_string()` member plus free helper and a `std::formatter` specialization naming the service and the pending-request count.

#### Scenario: Method ports render their state

- **WHEN** `to_string()` and `std::format("{}", port)` are evaluated on a client with outstanding requests
- **THEN** the text names the service and the pending count, and the formatter output equals the member output
