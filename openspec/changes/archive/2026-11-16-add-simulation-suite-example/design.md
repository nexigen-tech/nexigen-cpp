# Design

## Context

См. `proposal.md` — Why. Здесь только то, что определяет подход.

В репозитории уже есть два близких примера, и новый строится на их приёмах:

- `examples/integration/suite_2_apps` — два приложения, `com`-транспорт,
  `TraceHeader` на каждый сэмпл, iceoryx2-синки логов/метрик/трейсов, генерация
  suite-манифеста и конфигов демонов из скрипта.
- `examples/suite` — роли `worker`/`degrade`/`failure`: приложение само завершается
  по таймеру, а ExecutionManager поднимает его по политике перезапуска. Это точный
  прототип «глючного» приёмника.

Чего нет ни в одном примере: одновременной работы StateManager и
PlatformHealthManagement, объявленной Function Group с приложениями и сквозной
проверки надзора. Этот пример закрывает именно этот пробел.

Ограничения, которые нельзя обойти:

- всё, что использует `com`, собирается только при `NEXIGEN_ENABLE_COM=ON`;
- `nexigen-exec`, `nexigen-sm`, `nexigen-phmd` — отдельные процессы со своими
  конфигами; пример обязан их сгенерировать, а не хранить;
- приложение узнаёт Function Group только из lifecycle-события EM, а свой
  checkpoint-сервис — из своего аргумента; PHM должен получить и то, и другое.

## Goals / Non-Goals

**Goals:**

- Одна команда поднимает полный стек и показывает работающую надзорную петлю.
- Падение и подъём приложения детерминированы и наблюдаемы в консоли и в логах.
- Все три приложения инструментированы одинаково: логи, метрики, трейсы,
  готовность в EM, checkpoint'ы в PHM, чтение состояния из SM.

**Non-Goals:**

- Не демонстрировать PHM-инициированное восстановление в профиле по умолчанию
  (см. D3); вариант описан, но не включён.
- Не добавлять новых библиотечных API и не менять поведение модулей.
- Не упаковывать пример в контейнер и не описывать развёртывание на целевой машине.

## Decisions

### D1. Каталог и имена

```
examples/integration/simulation_suite/
  CMakeLists.txt
  vector_sample.hpp          общий payload + конверсии
  sim_common.hpp             общий каркас приложения (настройки, телеметрия, роли)
  ex_sim_generator.cpp
  ex_sim_receiver.cpp
  ex_sim_flaky_receiver.cpp
  config/                    локальные настройки приложений (логи/метрики/трейсы)
  settings/                  глобальные настройки suite
  run_simulation_suite.sh
  clean_simulation_suite.sh
```

Namespace `simulation_suite`, имена бинарников с префиксом `ex_sim_`. Префикс
сохраняет сортировку в дереве сборки рядом с `ex_generator`/`ex_receiver` и делает
принадлежность к примеру очевидной в `ps`.

### D2. Все конфигурации генерируются драйвером

Драйвер создаёт четыре набора в demo-root (`/tmp/opencode/nexigen-simulation-suite`
по умолчанию):

| Файл | Потребитель | Содержимое |
|---|---|---|
| `suite.json` | `nexigen-exec start --config` | Function Group `Simulation` + `RootFG`, три приложения, политика перезапуска, зависимости, CPU |
| `sm.json` | `nexigen-sm --config` | Function Group `Simulation` с переходами и приоритетами |
| `phm.json` | `nexigen-phmd --manifest` | три процесса, окна живости, checkpoint-сервисы, `recovery_timeout_ms` |
| `daemons/{logd,metricsd,traced}.json` | три демона | сервисы, каталоги вывода, аффинность |

Альтернатива — хранить манифесты в репозитории — отвергнута: в них должны быть
абсолютные пути к бинарникам и demo-root, а `suite_2_apps` уже установил правило
«никаких машинно-зависимых путей в репозитории».

### D3. Падение — аварийное завершение, поднимает ExecutionManager

`ex_sim_flaky_receiver` по таймеру корректно закрывает инфраструктуру и вызывает
`_exit(1)`. В `suite.json` он объявлен как `type: "daemon"`, поэтому EM трактует
выход как аварийное self-termination и применяет политику
`schedule_retry_or_fail` (`restart_attempts`, `restart_delay_s`).

Рассмотренные альтернативы:

- **PHM-восстановление** (`recovery_rules: [RestartProcess]`): PHM на `Expired`
  просит EM о перезапуске. Отвергнуто как профиль по умолчанию: EM и PHM начали бы
  перезапускать одновременно, а пример должен показывать предсказуемую лестницу.
  Вариант остаётся доступен правкой `phm.json`.
- **Чистое завершение с кодом 0 у `daemon`**: EM всё равно считает это аварийным,
  но код 0 маскирует «глючность» в `exit.json`. Отвергнуто.

Бюджет: `restart_attempts: 100`, `restart_delay_s: 1`. При периоде 15 с это
~25 минут демонстрации без исчерпания бюджета.

### D4. Payload и измерение задержки

```
VectorSample {
    uint64_t sequence;      // номер вектора, строго возрастает в процессе
    uint64_t sent_ns;       // метка отправки, steady_clock::now().time_since_epoch()
    double   values[10];    // значения вектора
}                           // 96 байт, trivially copyable
```

Задержка считается как `steady_clock::now() - VectorSample::sent_ns`. На Linux
`steady_clock` — это `CLOCK_MONOTONIC`, общий для всех процессов на машине, поэтому
разность корректна. Ограничение фиксируется явно: пример не рассчитан на несколько
хостов, где монотонные часы не синхронизированы.

`VectorSample` получает `to_string()`, `std::formatter` и ADL `to_json`/`from_json`
по требованию проекта: консольный вывод и диагностика используют одно
представление, а JSON-пара проверяется на устойчивость к враждебному вводу.

### D5. Один трейс на вектор

Генератор на каждый вектор делает `NEXIGEN_TRACE_NEW_ROOT`, открывает спан
`publish-vector` и кладёт `make_trace_header(...)` в `user_header` сэмпла — тот же
приём, что в `suite_2_apps`. Приёмник выставляет `current_trace_context()` из
заголовка и открывает `process-vector`, поэтому один trace id виден в логах
генератора и обоих приёмников.

### D6. Function Group `Simulation` и чтение состояния

`Simulation` объявляется в обоих манифестах с состояниями
`["Running", "SafeState", "Off"]` и переходами `Running→SafeState`,
`SafeState→Running`, `Running→Off`, `Off→Running`. Первое состояние — начальное,
поэтому SM публикует `Running` сразу после старта, и приложениям не нужен
дополнительный триггер.

Приложения читают состояние через `phm::SupervisedEntity::current_group_state`
(Field-паттерн, `history_size = 1`, без блокировки). В примере состояние
используется как переключатель: в `Off` приложение прекращает публикацию, в
`SafeState` — только логирует и ждёт.

### D7. Надзор PHM

`phm.json` объявляет три процесса с отдельными checkpoint-сервисами
`Nexigen/PHM/Simulation/<app>`, окном живости 2 с и
`failed_supervision_cycles_tolerance: 1`. Окно шире задержки перезапуска (1 с),
поэтому штатный подъём не превращается в `Expired`.

Правила восстановления по умолчанию пусты: при исчерпании допуска PHM эскалирует
группу в SM, а не перезапускает приложение сам. Watchdog выключен — пример не
должен трогать устройство на машине разработчика.

### D8. Порядок старта и готовность

```
logd, metricsd, traced
        |
        v
nexigen-exec  (suite: vector_receiver, flaky_receiver, затем vector_generator
               по dependencies: [vector_receiver])
        |
        v
nexigen-sm    (RootFG Verify/Run через EM)
        |
        v
nexigen-phmd  (узнаёт Function Group из lifecycle-событий EM)
```

Генератор объявляет зависимость от `vector_receiver` со состоянием `running`,
поэтому не начинает публикацию, пока приёмник не готов. `flaky_receiver`
независим: он должен переживать перезапуски в любом порядке.

PHM стартует последним: к этому моменту EM уже публикует lifecycle-события, и
Function Group для эскалации известна.

### D9. Границы CTest

Каждый бинарник получает smoke-тест на ~2 секунды в ограниченном режиме: без
демонов, без EM, с собственным каталогом настроек. Полный стек — только через
скрипт: 15-секундный цикл падений не должен попадать в обычный прогон тестов.

### D10. Ручки для сокращения прогона

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `NEXIGEN_SIM_PERIOD_MS` | 1000 | период публикации вектора |
| `NEXIGEN_SIM_EXIT_AFTER_S` | 15 | период падения «глючного» приёмника |
| `NEXIGEN_SIM_RUN_FOREVER` | — | неограниченный режим для suite |
| `NEXIGEN_SIM_WORKER_SECONDS` | 2 | длительность ограниченного smoke-прогона |

### D11. Project-local iceoryx2 configuration

Три приложения публикуют метрики в один сервис `nexigen/metrics/stream`, а
iceoryx2 по умолчанию разрешает только **два издателя на publish-subscribe
сервис**. Третий процесс не может открыть сервис, и `Iceoryx2MetricSink::start()`
возвращает `SystemError`.

iceoryx2 читает конфигурацию в порядке приоритетов, и первым идёт
**project-local** `./config/iceoryx2.toml` относительно рабочего каталога
процесса. Драйвер поэтому создаёт `${demo_root}/stack/config/iceoryx2.toml` и
запускает весь стек из этого каталога: каждый демон, Execution Manager и
запущенные им приложения наследуют рабочий каталог, а конфигурация пользователя
в `~/.config/iceoryx2/` не трогается.

Альтернатива — писать в домашний каталог пользователя — отвергнута: пример не
должен менять машинную конфигурацию. Альтернатива «по одному метрик-сервису на
приложение» отвергнута: метрик-демон слушает один сервис и перестал бы
агрегировать все три.

### D12. Память и конкурентность

Новых атомиков и разделяемого состояния между потоками пример не вводит, поэтому
`alignas(64)` и явные `std::memory_order` не применяются: каждый worker владеет
своим SPSC-буфером внутри модулей `logging`/`metrics`/`tracing`, как и в
существующих примерах.

Раскладка сообщения: `VectorSample` — 8 + 8 + 10×8 = 96 байт, остаётся в пределах
двух кэш-линий и передаётся через пул `com` без копирования. На один вектор
приходится один `loan_uninit`, ноль выделений в куче; `to_string` вызывается
только при печати в консоль (холодный путь).

### D13. Пробуждение по событию вместо опроса

Первая версия приёмников спала 50 мс между дренированиями очереди. Измеренная
«задержка передачи» тогда отражала период сна, а не транспорт: 8–11 мс, с
медленным дрейфом фазы по пиле 0–50 мс. Для примера, который показывает
HIL-подобную петлю, это вводило в заблуждение.

Решение: генератор после каждой успешной публикации кольцует
`Nexigen/Simulation/VectorsEvent`, а приёмники блокируются на
`com::WaitSet` с привязкой `com::EventListener`. Уведомление — счётчик, а
сэмплы остаются в очереди подписки, поэтому потерянное уведомление не теряет
данные: одно пробуждение дренирует всё накопленное.

Цена: одно событие на вектор (десятки наносекунд на `notify`) и один лишний
сервис в графе. Выигрыш: 140–460 µs вместо 8–11 мс и 0 % CPU в простое.

Таймаут WaitSet (200 мс) остаётся только для проверки состояния Function Group
и запроса остановки; если событийный канал открыть не удалось, приёмник
возвращается к фиксированному опросу 50 мс.

Остаток после этого — стоимость самого пробуждения (`epoll` → планировщик →
переключение контекста), а не передача сэмпла: пиннинг генератора и приёмника на
потоки одного физического ядра медиану не изменил (A/B: ~235 µs против ~231 µs,
разница в пределах шума). Поэтому добавлен **опциональный spin-режим**
(`NEXIGEN_SIM_SPIN=1`): приёмник не блокируется, а крутится на `receive()`.
Замер: 44–120 µs против 173–265 µs, цена — 100 % одного ядра. По умолчанию
режим выключен: демонстрация должна оставаться дружелюбной к машине.

Последний слагаемый остаток — очередь планировщика. Для него добавлен
опциональный `NEXIGEN_SIM_RT_PRIORITY`: приложение переводит свой цикл в
`SCHED_FIFO` через `core::ThreadSpec`/`apply_thread_spec_self`, а в манифесте
приёмники объявлены с `allow_rt_priority: true`, чтобы привилегированный
Execution Manager не срезал `CAP_SYS_NICE` у ребёнка.

Важная деталь: `apply_thread_spec_self` в необязательном режиме возвращает
успех, даже когда ядро отказало в политике, — отказ виден только в
`ThreadApplyReport::failed()`. Обёртка проверяет именно отчёт, иначе приложение
логировало бы «SCHED_FIFO priority 50», оставаясь на `SCHED_OTHER`.

### Замер против «90–100 ns» из документации iceoryx2

Цифра iceoryx2 измеряет **передачу уже займованного чанка** в горячем цикле: обе
стороны крутятся, данные в L1, ни аллокации, ни пробуждения. Наш замер — полный
путь приложения: генерация десяти значений, займ чанка, публикация, уведомление,
приём. Разложение по шагам (Release-сборка, spin-режим):

| Шаг | Время |
|---|---|
| генерация 10 значений | < 1 µs |
| `loan_uninit` | 5–13 µs |
| `send` | 2–4 µs |
| видимость + `receive` | 1–3 µs |
| **итого** | **8–17 µs** |

То есть собственно публикация — единицы микросекунд, и разрыв с 90 ns объясняется
частотой ядра (в простое 48 %), холодными кэшами после секундного сна и двумя
подписчиками, а не накладными расходами обёртки.

`loan_uninit` доминировал потому, что займ трогает метаданные пула чанков в
разделяемой памяти, а после секундного сна эти строки кэша холодные. Лечится
предзаёмом: генератор держит один чанк займованным и берёт следующий сразу после
`send`, пока пул и сегмент горячие. Замер (Release, spin):

| | до предзаёма | после |
|---|---|---|
| `loan_uninit` | 5–13 µs (холодный) | ~3 µs (горячий, вне критической секции) |
| `publish_cost_us` | 7–15 µs | ~7 µs |
| end-to-end | 8–17 µs | **4–8 µs** |

Пустой пул не ломает публикацию: предзаём возвращает `std::nullopt`, и следующий
вектор займовается синхронно внутри критической секции.

Отдельно: **Debug-сборка искажает картину в 7 раз** (72–116 µs против 8–17 µs),
поэтому драйвер печатает предупреждение, если выбранное дерево не Release.

Измерить выигрыш RT-политики на текущей машине нельзя: `RLIMIT_RTPRIO = 0`, capabilities нет,
`chrt -f` отвечает `Operation not permitted`. Поэтому проверен только путь
деградации; сам эффект измеряется на хосте с `rtprio` в `limits.conf` или под
root.

## Risks / Trade-offs

- **[Демонстрация долгая: 15 секунд на цикл]** → ручки D10 и smoke-тесты D9; полный
  прогон остаётся ручным.
- **[Бюджет перезапусков исчерпается на длинном прогоне]** → `restart_attempts: 100`
  и `impact_on_app_suite_operability: degrade`, чтобы один приёмник не валил suite.
- **[SM гейтится на RootFG от EM]** → драйвер поднимает EM раньше SM; при отсутствии
  EM у SM есть синхронный fallback, но пример на него не рассчитывает.
- **[PHM не знает Function Group до первого lifecycle-события]** → PHM теперь
  дренит lifecycle-канал каждый цикл, а при неизвестной группе фиксирует fault
  `UnknownGroup` вместо тихого дропа; порядок старта D8 делает окно пустым.
- **[Гонка discovery iceoryx2 при старте]** → драйвер ждёт маркеры готовности
  процессов и только затем запускает suite; приложения повторяют публикацию
  готовности.
- **[Монотонные часы общие только в пределах машины]** → ограничение зафиксировано
  в D4; пример не позиционируется как межхостовый.

## Migration Plan

Изменение аддитивное: новый каталог плюс одна строка `add_subdirectory` в
`examples/integration/CMakeLists.txt`. Откат — удалить каталог и строку; на
библиотечные модули это не влияет.

## Open Questions

Нет. Все развилки, влияющие на спеки и задачи, закрыты решениями D1–D11.
